# CLOVER 시나리오 검토·수정안 v3

작성: 2026-11-13. 대상: 팀원이 공유한 「CLOVER 시뮬레이션」 요약과 현재 main. 모든 제원은 연구용 설계값이며 실제 공장 권장 제원이 아니다.

최종 검수에서 알고리즘·시나리오·도출 결론을 연결한 [평가 요약](SCENARIO_EVALUATION_FINAL_REVIEW.md)을 추가했다. 본문의 E0~E3는 PRD와 같은 단계 이름을 쓰며, 휴리스틱 가중치는 고정한다. 62개 조건은 실행 전 설계 상태다.

**판정: 실험의 방향은 좋다. 다만 현재 요약을 그대로 실행해 알고리즘의 우열을 결론 내리기에는 부족하다.** 알고리즘 연결 상태, 부하 산정, 진행 중 대기 통계와 모델이 표현하는 작업의 의미부터 수정해야 한다. 아래는 시나리오 담당자에게 전달할 수 있는 수정 설계다.

검토 기준 코드는 main `b4861d0f0cf8f975243c802e1f597662a26cb948`이다. 별도 언급이 없는 구현 사실은 이 버전 기준이다. 원문이 언급한 `CLOVER_6시나리오_구체화_v2.md`, `CLOVER_시나리오_추가6종.md`, `lambda_calc.py`의 실제 파일은 이번 입력에 없어, 그 안의 좌표·수식·코드를 검수한 것은 아니다. 기존 P4 진단 실험을 참고했으며 **아래 62개 설계 셀의 새 시뮬레이션을 실행한 결과는 아니다.**

## 1. 좋은 점과 반드시 고칠 점

유지할 부분은 같은 입력을 정책별로 공유하는 원칙, 처음부터 승자를 정하지 않는 목적, 입력 목적지 비중과 실제 층간 이동의 구분, 화폐 수익을 보조 지표로 두는 판단이다. 여유·혼잡·충전·긴급·다층·과부하를 포함한 12개 분류도 출발점으로 적절하다.

| 원문 | 수정·이유 |
|---|---|
| 배정 MILP·CP-SAT은 연결되지 않음 | 현재 7개 정책이 headless에 연결돼 있다. 3종만 비교한다면 구현 한계가 아니라 실험 예산에 따른 선택이라고 써야 한다. |
| 특정 λ가 통로·충전·캐빈 과부하를 만든다 | 지도·로봇 수·작업시간·충전량을 반영해 확인할 **파일럿 후보**다. `L=20m`만으로 병목이나 과부하를 확정할 수 없다. |
| 캐빈 2개면 용량 2배 | 두 캐빈이 실제 경로에 쓰이는지부터 확인한다. 공차 회송·문 시간·경로 선택·다른 병목 때문에 처리량이 2배가 된다는 보장이 없다. |
| 진행 중 대기까지 합쳐 P50/P95 | 끝난 대기와 진행 중 대기를 분리한다. 현재까지 30초 기다린 작업의 최종 대기가 30초라는 뜻은 아니다. |
| 항상 한 축만 바꾼다 | 1단계는 한 축씩 바꿔 원인을 확인하고, 2단계는 사전 지정한 2×2 조합으로 상호작용을 확인한다. |
| burst ×2/×4 | 평균 부하까지 커지는 실험과, **총 작업 수를 유지한 채 몰림만 커지는 실험**을 구분한다. |
| seed를 늘리면 유의하다 | 반복 수만으로 보장되지 않는다. 효과 크기·변동·검정력과 독립적인 지도 다양성이 필요하다. |
| 폭 1.3/2.2/3.1m는 언제나 1/2/3대 | 로봇 폭 0.6m·측면 여유 0.3m·벽 여유 0.4m일 때의 공유 폭 예산이다. 이종 로봇에는 단순 대수표를 그대로 적용하지 않는다. |

단일 요인 실험만으로는 “좁은 통로와 낮은 배터리가 함께 나타났을 때”를 설명하기 어렵다. 목적별 설계와 요인 조합을 구분하는 근거는 [NIST 실험 설계 안내](https://www.itl.nist.gov/div898/handbook/pri/section3/pri33.htm)를 참고한다.

## 2. 현재 구현에 맞춘 비교 대상과 한계

| 정책 ID | 역할 | 이번 설계에서의 위치 |
|---|---|---|
| `baseline` | 작업 FIFO + 로봇 라운드로빈, 반응형 충전 | 단순 정책 대조군. 의도적으로 약화하지 않는다. |
| `optimized` | 거리·배터리·대기·납기 등을 고려하는 가중치 휴리스틱 | 실용 기준 정책. 기존 기본값 유지. |
| `assignment_milp_legacy` | 기존 배정 MILP | 배정 개선과 RH 계획의 차이를 보는 보조 비교 |
| `rh_milp_grid` | 시간 격자 기반 Rolling Horizon MILP | 핵심 비교 |
| `rh_cpsat_linear` | 같은 격자 모델 계열의 CP-SAT | MILP와 모델 범위를 맞추는 핵심 비교 |
| `rh_cpsat_interval` | 격자 모델의 interval 표현 | 모델 표현 차이의 보조 비교 |
| `rh_cpsat_native` | 별도 시간·구간 표현의 CP-SAT | 실용 후보 추가 비교. 격자·계획 범위가 다르면 solver만의 차이라고 부르지 않는다. |

1차 핵심 비교는 `baseline / optimized / rh_milp_grid / rh_cpsat_linear` 4종이다. native는 공동배차·충전·다층·규모/예산에서 먼저 추가한다. 기능 검증은 7종 모두 한다. 실제 정책 목록은 [scenario.py](https://github.com/tortoiese/CLOVER/blob/b4861d0f0cf8f975243c802e1f597662a26cb948/robot_factory_sim/simulation/evaluation/scenario.py)에 있다.

이는 같은 공장 입력을 주는 **운영 정책 비교**다. 정책별 실행 상태는 이후 달라질 수 있으므로, solver 자체의 성능을 분리하려면 같은 snapshot·후보·목적·예산을 고정한 MILP/CP-SAT 대조를 별도로 해야 한다. native는 실제 비교한 가족에서만 추천 후보로 올린다. legacy와 RH의 차이를 rolling horizon 한 요소만의 기여로 해석하지 않는다.

기존 작업에서도 시나리오에 따라 결과가 달랐다. 작은 공동배차 D0 배치에서는 휴리스틱15.1s 대비 MILP12.5s로 완료가 빨랐지만, 충전 λ=0.08·1,800s·D1·seed1001에서는 완료 수가 휴리스틱128/130, MILP126/130이었다. 이는 작은 진단 사례이며 일반적인 우열의 근거가 아니다. 공동배차를 핵심에 넣고 충전을 길게 관측해야 하는 이유다. 수치와 한계는 [P4_REVIEW.md](P4_REVIEW.md)에 보존돼 있다.

현재 모델은 **로봇이 설비로 이동해 작업하는 동안 로봇도 점유되고, 완료 뒤 그 위치에 남는 구조**다. 일반적인 화물 pickup→delivery 운송, 공정 BOM·버퍼, 연속 공간 충돌·가속도 모델까지 구현한 것으로 해석하지 않는다. 경로 후보도 현재 K=1이므로 지도에 우회로를 그렸다는 이유만으로 전역 경로 최적화를 했다고 주장할 수 없다.

따라서 목적지 50%를 위층으로 정해도 실제 왕복은 50%가 아니다. 통로·다층의 **첫 기전 확인은 모든 로봇을 한쪽에 놓고 반대쪽 작업을 동시에 넣는 유한 배치**로 한다. 지속 부하에서는 실제 통과 수·층간 이동 수·충전 왕복이 충분한지 별도로 확인한다. 정책의 완료를 기다렸다가 다음 작업을 넣거나 로봇을 매번 원위치로 순간 이동시키면 공통 외생 입력 비교가 깨진다.

현재 가능한 입력과 추가 작업을 구별한다.

| 항목 | 현재 지원·주의 |
|---|---|
| 일정 도착률 Poisson | `workload.kind=poisson`, `rate`는 tasks/s. `rate=0`도 가능. |
| burst·긴급 비중·목적지 비중·적합 설비 집합 | 미리 만든 `workload.kind=trace`로 입력한다. 임의의 `burst_ratio` 등을 Scenario JSON에 넣으면 안 된다. |
| 이종 로봇 | 속도·폭·길이·배터리·소모량 등 물리 차이를 비교한다. `robot_type` 이름만으로 작업 자격이 제한되지는 않는다. |
| 교란 | `station_active`, `charger_active`, `robot_retire`, `edge_width`, `cancel_task` 지원. retire는 영구 퇴역이다. |
| 아직 없는 Scenario 입력 | 퇴역 로봇 수리·재가동, 캐빈 고장 주입, 통신 지연 주입, 캐빈 동시 2대 탑승. 별도 구현 후 다룬다. |
| 대기·자원 | 원시 요청/확보/해제 및 대기 집계는 있다. 모든 자원의 통일된 이용률 표, suite 통계·최종 추천은 후처리가 더 필요하다. |

## 3. λ를 정하는 방법: 숫자보다 기준을 먼저 고정

### 3.1 단위를 맞춘 1차 계산

참조 작업 1건이 자원 r을 쓰는 양을 `D_r_ref`(자원 단위·초/작업), 자원 용량을 `C_r`(자원 단위)라고 두면:

```text
μ_r_nominal = C_r / D_r_ref       [작업/초]
μ_ref = min_r μ_r_nominal
λ_candidate = ρ × μ_ref
```

로봇은 robot·s, 단일 설비·캐빈은 slot·s, 통로는 mm·s로 단위를 맞춘다. 동질 로봇일 때만 통로 폭 예산을 정수 대수로 바꿔 계산할 수 있다. 충전은 `총 슬롯 × 슬롯당 충전율 / 작업당 보충 에너지`로 별도 에너지 수지를 확인한다. 로봇의 작업·충전·이동 시간은 서로 묶여 있으므로 중복 계산과 누락을 점검한다.

이 식은 **참조 경로·작업 배합에 대한 명목 추정**이다. 모든 작업이 반드시 쓰는 자원의 점유량이 고정돼 있을 때 상한으로 사용할 수 있지만, 설비 배정·충전 전략·로봇의 현재 위치에 따라 점유량이 달라지면 전역적인 처리 용량 상한이라고 단정하지 않는다. 간섭·회송·동시 자원 확보 때문에 실제 처리량은 단순 추정과 달라질 수 있다.

예를 들어 충전 1슬롯, 슬롯당 0.25 battery-unit/s일 때 작업당 보충량이 5이면 명목 용량은 0.05 tasks/s다. λ=0.04는 이용률 0.8이다. 보충량이 8이면 용량 0.03125, 이용률 1.28이다. **같은 0.04가 저부하일 수도 과부하일 수도 있다.** 초기 SOC가 높은 짧은 실행은 충전 병목을 숨길 수 있다.

### 3.2 고정할 부하와 바꿀 부하

각 비교 블록의 참조 지도·참조 배합에서 λ₀를 한 번 정한다. 폭 1.3→2.2→3.1m 또는 충전 1→4슬롯 비교에서는 **동일 절대 λ·동일 작업 trace**를 유지한다. 변형 지도마다 λ를 다시 용량에 맞추면 자원 증설 효과와 수요 증가가 섞인다. 정책마다 용량을 따로 추정해 λ를 바꾸어서도 안 된다.

training에서 `ρ=0.25/0.70/0.95/1.10` 등의 후보를 점검하되, 최종 held-out에서는 사전에 고정한 값만 쓴다. 자원 노출·대기·backlog를 보고 실제 병목을 확인한다. 특정 정책에 유리하게 λ를 골라 고정하지 않는다.

| 기존 후보 | 수정 판정 |
|---|---|
| S00 0.03/s | 저부하 후보. 실제 참조 용량 대비 여유를 확인한다. |
| S02 0.10/s | 지속 통로 과부하로 단정하지 않는다. 먼저 유한 배치 폭 대조군을 검증하고, 지속 실험은 실제 횡단 수요를 확인한 뒤 λ 고정. |
| S04 0.04/s | 충전 부족을 보장하지 않는다. 에너지 수지·충전 반복·측정 구간 최종 SOC로 검증. |
| S06 0.17/s, ×2/×4 | 평시 부하의 타당성부터 확인하고, 평균 보존 burst와 평균 증가 burst를 구별. |
| S08 0.08/s | **4.8건/분**이다. 두 캐빈 활성화가 용량·λ 2배를 뜻하지 않는다. |
| S10 0.22/0.26/s | λ₀=0.20의 근거 필요. 예: 로봇 4대, 모든 작업이 로봇을 20초 점유한다면 이동·충전을 빼도 낙관적 상한은 4/20=0.20/s. 이 명시 조건에서만 두 값이 상한 초과라는 근거가 생긴다. |

## 4. 다양성 수정: 12개 주제, 기본 46셀 + 복합 16셀

핵심은 **8종(S00·S01·S02·S04·S06·S08·S10·S11)**, 보조는 4종(S03·S05·S07·S09)으로 제안한다. 공동배차는 최적화 선택의 효과를, 규모·예산은 계산 지연으로 이득이 사라지는 경계를 확인하므로 핵심으로 올린다. 보조라고 검증을 생략하지는 않는다.

각 행의 조건은 서로 다른 설계 셀이다. 유한 배치는 λ를 붙여 정상상태 처리량 실험처럼 해석하지 않는다. 절대 좌표·로봇 목록·trace가 확정되기 전에는 모두 **설계 상태**다. 기계 판독용 목록은 [experiment_design_v3.json](scenarios/experiment_design_v3.json)에 있다.

| ID / 기본 셀 수 | 확인할 질문·변경 축 | 고정·대조·주 지표 |
|---|---|---|
| S00 여유·음성 대조 / 4 | 도착 0; 참조 ρ=0.25; 같은 낮은 부하에서 폭 1.3/1.8m | 무작업 때 작업 생성 0 확인. 1.3/1.8은 동질 로봇의 입장 용량이 같다는 대조. 저부하에서 계산 비용 대비 이득이 작은지도 본다. 모든 KPI가 같아야 한다는 가정은 하지 않는다. |

S02의 폭은 대향 통행도 같은 mm 예산을 공유한다. 이는 명시적인 차선 배치나 실제 공장의 충돌 안전성 증명이 아니다. [공통 통로 계약](https://github.com/tortoiese/CLOVER/blob/b4861d0f0cf8f975243c802e1f597662a26cb948/robot_factory_sim/simulation/traffic_rules.py)을 기준으로 확인한다.

### 평균을 보존하는 burst

비교 대상 도착 구간 중 burst 비율 `f=0.1`, 평균 도착률 λ₀, burst 배수 b라면:

```text
λ_peak = b × λ₀
λ_off = λ₀ × (1 - b×f) / (1-f)    (b×f < 1)
λ₀=0.17, b=2 → peak 0.34, off 0.151111…
λ₀=0.17, b=4 → peak 0.68, off 0.113333…
```

이는 기대 평균을 보존하는 식이다. 실제 비교에서는 같은 seed의 N개 작업을 먼저 만들고 UID·목적지·noise·우선순위를 보존한 채 도착시각을 위 누적 강도의 역함수로 재배치해 **실제 작업 수도 동일하게** 한다. 납기는 새 도착시각+입력 기반 동일 slack 규칙으로 만든다. 시작안은 측정 구간의45~55%를 burst로 하고 warmup 도착은 같은 평탄 trace를 쓰는 것이다. 우선순위 비중만 바꾸는 셀에서는 납기까지 바꾸지 않는다. 긴급은 priority0, 일반은 priority2로 고정하고 동일 UID 표본에 라벨을 부여한다. 평균이 커지는 burst는 별도 연구 질문으로 추가할 수 있지만 이 다섯 셀과 혼합하지 않는다.

## 5. 비교의 공정성과 측정 규칙

### D0와 공통 D1을 분리

- D0: 판단으로 인한 시뮬레이션 지연을 제외한 계획 선택 효과. 실제 wall 계산시간은 함께 저장한다.
- D1: **전체 정책의 공통 staged controller**를 사용해 worker 준비·판단·검증·공개 지연을 포함한다. 운영 성능 결론은 이를 주 비교로 삼되, 현재 controller·설정까지 포함한 결과라고 명시한다.
- 공통 D1은 `--decision-settings`로 켠다. RH 수학 설정의 `timing_mode=D0`와 함께 사용한다. 구형 RH 전용 `timing_mode=D1`을 다른 정책 D0와 섞으면 안 된다.
- S11 예산은 외부 실행 watchdog이 아니라 공통 결정 설정의 `end_to_end_soft_deadline_seconds`다. publication 여유·fallback·worker 시작 한도·메모리·재시도도 명시한다. 예산0.5s에서 cold 준비가 성공할 것이라고 가정하지 않는다.
- 기존 P4의 guard0.2s는 해당 파일럿에서 확인한 값이다. 장비·부하가 달라져도 충분하다고 보장하지 않는다. E1에서 정하고 E2 전에 고정한다. OS·Python·CPU·solver 버전/worker 수·고해상도 clock 구현과 해상도·peak memory 측정 범위(자식 포함 여부)를 기록한다.

현재 구현과 과거 파일럿 한계는 [P4 검토](P4_REVIEW.md), 실제 공통 D1 사용법은 [D1_STARTUP.md](../robot_factory_sim/D1_STARTUP.md)를 따른다. GUI의 live 실행 결과와 headless D1을 같은 시간 규약으로 합치지 않는다. 현재 `optimized` 기본 정책·D0 기본 모드는 변경하지 않는다.

### 입력과 관측 구간

- 정책 간 같은 trace 해시, 작업 UID/적합 설비/처리 noise, t=0 로봇 위치·SOC·캐빈 층, 교란 시각을 공유한다. 모델 범위·후보 수·solver seed·horizon·재계획 주기·메모리와 예산도 manifest에 남긴다.
- 정책별 내부 후보 제외 사유는 결과이지 입력을 사후 맞출 이유가 아니다. 자원 사용이 예상과 다르다고 정책별 목적지 비중을 바꾸지 않는다.
- 유한 배치는 warmup=0. 전부 완료했을 때만 makespan을 비교한다. 미완료면 NA와 완료 수·미완료 수·최고령 나이를 함께 표시한다.
- 지속 입력은 warmup600s+측정7200s, 총7800s를 **E1 검증 후보**로 둔다. 정상상태 보장은 아니다. 충전은 로봇별 충전 반복과 에너지 수지를 확인해 구간을 정한다.
- 정책별 warmup 종료 상태가 다른 것은 정책 효과다. t=600에 SOC·위치·대기열을 강제로 같게 리셋하지 않는다. carry-in 작업·대기를 따로 표시한다.
- 과부하는 정상상태 평균을 요구하지 않는다. 사전 고정 시간창의 backlog 증가, 취소와 퇴역을 반영한 미완료, 납기 위반과 서비스 편향을 비교한다.

### 대기·납기·에너지

| 지표 | 함께 제시할 항목과 해석 |
|---|---|

| 작업 대기/리드타임 | 시작/완료된 표본의 P50·P95와 표본 수, 아직 시작/완료하지 않은 수와 현재 나이. 서로 다른 코호트의 수치를 혼합하지 않음. |
| 자원 대기 | 완료 확보 대기(`granted_wait`), 철회까지 경과, 종료 시 미확보 나이(`right_censored_ages`), carry-in, 대기 면적 robot·s를 분리. |

| 납기 | 현재 구현은 측정창 안에 납기가 온 작업을 분모로 하며 미완료도 위반에 포함. 납기 전에 취소된 작업은 제외되므로 취소 수도 별도 표시. |

현재까지의 대기 나이는 최종 대기보다 작거나 같은 **우측 중도절단** 관측이다. 완료된 대기와 단순 합쳐 P95를 계산하면 왜곡될 수 있다. [NIST 중도절단 설명](https://www.itl.nist.gov/div898/handbook/apr/section1/apr131.htm)처럼 이를 구분해야 한다. 현재 집계는 Kaplan–Meier 같은 생존 추정이나 별도 drain 완료 관측을 자동 제공하지 않는다. 이를 쓰려면 추가 분석과 코호트 정의가 필요하다. 검열 때문에 P95를 추정할 수 없으면 NA로 남긴다.

물리 감사·에너지 보존·raw 재구성·replay·worker 실패 상태를 같이 저장한다. timeout·guard 실패·OOM·도달 불가 결과를 성공 결과에서 조용히 삭제하거나 0점 결과로 바꾸지 않는다. 실행 실패율은 전체 시도 기준으로 보고, KPI는 유효한 paired 표본 범위를 명시한다. 자원 기전 검사가 실패한 지도는 E2 전에 수정/재검증하고, 이미 얻은 실패 기록은 보존한다.

기전 검사는 사전 지정한 참조 실행·경로 검사로 자원이 실제 존재하고 사용 가능한지 확인하는 절차다. **모든 정책에서 대기가 발생하거나 추가 캐빈이 똑같이 사용되어야 한다는 통과 조건은 두지 않는다.** 계획으로 대기를 피하거나 자원 사용을 바꾸는 것 자체가 정책 효과일 수 있다. 정책별 자원 사용은 결과로 모두 남기고, 유리한 정책만 통과시키는 지도/seed 사후 선별은 금지한다.

## 6. 단계별 실행과 반복 수

| 단계 | 할 일 | 통과 기준 |
|---|---|---|
| E0 계약·기전 검사 | 12가족 대표 지도, 7정책 D0. 공동배차·통로·충전·긴급·다층·예산의 공통 D1 추가 검사. 위 검증 대조군 확인 | JSON 검증, 동일 입력, raw/replay, 물리/에너지 감사. 자원 변경이 실제 자원·경로에 반영됐는지 확인. |
| E1 파일럿 | 기본46셀과 복합16셀 설계. 무작위 입력 셀은 우선3seed, 완전 결정적 배치는 1trace. 실행 시간 보고 예산 확정 | λ 참조·실제 병목·warmup·충전 반복·예산/guard·native 범위 확정. 실패·차이 없음도 기록. |
| E1 학습·고정 | 물리 셀과 별개로 horizon·step·후보 수·native visits·cold/eager를 training에서 비교 | 정한 정책별 설정과 코드/지도/trace/환경 해시를 새 protocol에 고정. 기존 `P4_TRAINING_PROTOCOL.json`의 과거 freeze는 덮어쓰지 않음. |
| E2 held-out | 새 지도·새 수요 seed에서 고정 설정만 비교 | 중요한 결론의 각 leaf 조건에 우선 ≥3지도·지도당30 paired seed를 계획하고, 파일럿 변동·효과·예산으로 정당화. 이 숫자 자체가 유의성 보장은 아님. |
| E3 stress | E1과 분리한 새 입력으로 고부하·교란·작은 예산의 경계를 검증 | 지원 범위·실패·미완료·fallback을 보존. 결과를 보고 E2/E3 설정을 재튜닝하지 않음. |
| 최종 분석 P6/R7 | E2·E3의 정책 차이·신뢰구간·계산비용·실패율을 함께 정리 | “이 조건에서 이득”, “실용 차이 작음”, “예산 내 실패”, “근거 부족”을 구분. 일반화 범위를 명시. |

완전 결정적 trace·초기 상태·noise가 그대로라면 이름만 다른 seed 30개는 독립적인 수요 실험 30개가 아니다. 배치는 거리 배치·초기 위치·작업 순서가 다른 사전 생성 지도/trace로 반복한다. solver seed 반복은 계산 변동을 확인하는 별도 층이며 수요 반복을 대신하지 않는다.

같은 지도·seed·입력의 차이 `d=RH−optimized`를 기본 비교량으로 한다. 처리량은 양수가, 대기/납기 위반/계산시간은 음수가 유리하다고 명시한다. baseline 대비 효과도 함께 제공한다. 지도별 차이와 지도 내 paired 반복을 나누어 제시하고, 모든 seed를 독립 지도처럼 합치지 않는다. 여러 정책/지표를 탐색할 때 주 가설·주 지표를 사전 지정하고 다중 비교 조정 또는 탐색 결과임을 명시한다.

기존 지시와 PRD에 따라 `optimized`의 가중치는 이번 실험에서도 고정한다. RH의 horizon·격자·후보·예산 등을 training에서 선택했다면 “학습한 RH와 기존 기본 휴리스틱의 비교”라고 표기한다. 같은 문제의 MILP/CP-SAT 비교는 같은 후보 설정과 학습 예산으로 구성하고, 모든 알고리즘을 같은 방식으로 튜닝했다고 주장하지 않는다. solver만 비교할 때는 snapshot·목적함수·격자·후보·범위도 같게 한다.

최종 추천은 시나리오별 주 지표에서 사전 정의한 실용 개선을 보이면서 납기·미완료·실패율 한도를 지키는지로 정한다. 지표가 서로 충돌하면 하나의 종합 점수로 숨기지 말고 비용과 효과를 함께 제시한다. 물리적 용량을 넘는 과부하에서는 어떤 배정 알고리즘도 자원 부족 자체를 없앨 수 없다. 추천 범위는 실제로 검증한 정책·지도·예산 조건 안으로 제한한다.

신뢰구간·검정력은 효과와 분산에 따라 달라진다. [NIST 표본 수 안내](https://www.itl.nist.gov/div898/handbook/prc/section2/prc222.htm)를 근거로 파일럿 후 반복 수를 산정한다. 0을 포함한 차이의 신뢰구간만으로 두 정책의 동등성을 증명했다고 하지 않는다. “실용 차이 없음”을 주장하려면 허용 차이와 그 근거를 미리 정하고 적절한 동등성 분석이 필요하다. 현재 CLI는 suite 전체 통계나 자동 추천까지 구현한 상태가 아니다.

실행량의 예산 예시(아직 실행하지 않음): 기본46셀 중 완전 결정적12셀·무작위34셀에 각각1/3trace를 쓰면 114 paired 블록이다. 4정책 D1=456회, 결정적12셀의 4정책 D0=48회, 선택17셀 native 추가=39회, 복합16셀×3seed×4정책=192회로 **735회**다. 별도의 E0 대표 지도 12×7 D0 + 6×7 D1은126회다. 이는 첫 설계의 예산 예시이며 E2 횟수가 아니다. 시간·메모리 파일럿 후 **결과를 선별하지 않는 규칙으로 본격 E1 전에 범위를 줄일 수 있다.**

735회는 셀별 대표 지도와 한 묶음의 정책 설정에 대한 screening 예시다. 모든 지도 반복·설정 튜닝·동일 snapshot 대조·E2/E3를 포함한 총 실행 수가 아니다. 기존 PRD의 2,700회 초안과 더해서 사용하지 않으며, 최종 실행량은 새 protocol에서 단계별로 다시 고정한다.

## 7. 시나리오 담당자에게 요청할 납품물

1. 각 기본 셀/복합 모서리에 대한 실제 `clover-scenario-v1` JSON과 지도 도면. JSON 검증 전에는 “실행 완료/실행 가능”으로 표시하지 않는다.
2. 노드 ID/좌표/층/`node_type`, 엣지/방향/폭/활성, 로봇 ID/물리 제원/t=0 위치·SOC, 캐빈별 초기 층, 설비별 작업 유형·시간 분포, 충전소별 슬롯·슬롯당 rate를 확정한다.
3. trace 생성 규칙과 결과 trace: UID·도착·nominal·allowed·operation·priority·noise·deadline. 납기는 입력 기반 기준으로 고정하고 어떤 정책의 완료시각으로 만들지 않는다.
4. λ 산정표: `C_r / D_r_ref`, 거리 기준·경로·점유·충전 에너지·빈 캐빈 회송 가정, 계산 단위, 참조 지도와 λ₀. 기존 `lambda_calc.py` 실제 파일도 함께 전달해 단위·자원 결합·변형마다 λ가 바뀌는지 검수한다.
5. 기전 확인표: S02는 실제 공유 통과, S03는 실제 intersection 자원, S04는 충전 반복, S08는 두 캐빈 사용. S05·S10는 로봇/설비 작업 점유 수지. 미작동 대조군은 그대로 성능표에 넣지 않는다.
6. E1 설정·seed/지도 분리·주 지표·허용 차이·계산 예산 확정 후 새 freeze manifest 작성. 제3자가 같은 코드로 재실행할 수 있도록 해시와 명령을 보관한다.

현재 있는 작은 진단 지도를 검증하는 명령 예시는 다음과 같다(새 62개 셀을 생성/실행하는 명령은 아님).

```bash
# 저장소의 robot_factory_sim 디렉토리에서, 의존성이 설치된 Python 사용
python -m simulation.evaluation validate --scenario examples/p4/P4_S02_narrow.json
python -m simulation.evaluation --help
```

동봉한 `experiment_design_v3.json`은 **실험 설계 목록**이다. Scenario JSON이 아니며 `--scenario`에 넣으면 안 된다. 실제 지도/trace/설정 작성과 E0 검사를 통과한 후 실행 목록으로 변환한다. 이 문서 변경에는 알고리즘·GUI·기본 정책 변경이 포함되지 않는다.
