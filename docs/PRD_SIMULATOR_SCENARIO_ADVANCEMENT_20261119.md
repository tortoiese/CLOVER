# CLOVER 시뮬레이터 고도화·후속 실험 계획서

작성일: 2026-11-19 KST · 문서 버전: 0.1 · 상태: **계획 작성 완료 / 선행 수정·입력 생성·새 실험 미실행**

## 0. 한눈에 보는 목표와 실행 순서

같은 작업·같은 초기 상태에서 휴리스틱, RH MILP, RH CP-SAT을 비교하고, **어느 환경에서 추가 계획 계산이 필요한지와 그 선택의 한계**를 설명한다. 처리량·납기·에너지·계산시간을 함께 평가한다. 특정 알고리즘이 항상 이긴다는 결론을 목표로 정하지 않는다.

```text
M0 공통 제어·backend 준비 문제 수정 및 검수
 → M1 입력 생성·관측창·실행 예산·지표 계약 검수
 → M2 부하 × 충전 슬롯 × 도착 형태 개발 실험: D1 360회
 → M3 다른 구조의 지도·새 수요로 검증: D1 240회
 → M4 표본 수·가설·선택 규칙 등록 후 별도 확인 실험
```

1차 핵심 질문은 “들어오는 일이 늘고 충전기가 부족해질 때 RH의 이점이 언제 생기는가?”다. **18조건×새 수요 seed5개×4정책=360회**를 개발 평가의 기본 규모로 둔다. 먼저 고른 도착9조건180회, 이후 급증9조건180회를 실행한다. 준비 검사와 독립 지도 검증은 이360회에 합치지 않는다.

설계 JSON은 [기계 판독용 초안](scenarios/scenario_advancement_20261119/design_draft.json), 팀원 전달 사항은 [시나리오 담당자 작업 안내](scenarios/scenario_advancement_20261119/TEAM_SCENARIO_BRIEF.md)에 정리한다. **이 JSON은 현재 실행기가 읽는 시나리오 파일이 아니다.** 생성·감사·실행 지원을 보완하고 아래 게이트를 통과한 뒤 새 입력 묶음을 만든다.

## 4. M0 — 실험 신뢰성 선행 수정

### 4.1 일시 진입 정지 처리

현재 확인된 반례는`pause_admission()`이 안전한 drain을 위해 용량을0으로 만든 동안, 관측의 이동표 생성이 이를 폭 부족으로 해석해`TrafficBlocked`를 내는 것이다.

요구사항:

- 기하학적으로 통과할 수 없는 경우와 임시로 새 진입을 보류하는 상태를 구분한다.
- 기존 점유·원자적 확보·후미 해제를 유지한다. 이미 이동 중인 로봇의 자원을 강제로 빼앗지 않는다.
- 임시 보류 시 관측·배정·보조 충전 요청이 명시적으로 대기/거절·재관측하도록 한다. 예외를 무조건 성공 처리하지 않는다.
- 실제 통행 불가에는 기존 거부를 유지한다. 영구 폐쇄를 무료 이동으로 바꾸지 않는다.
- 폭 변경 요청·drain 시작·실제 용량 활성화·복원 활성화 시각을 각각 기록한다. 현재 로그에서 부족한 항목은 계측을 추가한다.

필수 회귀: 정상→일시 정지→폭 변경→재개, 실제 폭 부족, 충전 callback과 변경의 겹침, 배정 callback과 변경의 겹침, 연속 변경 요청, 종료 시 미해제 자원, 변경 전후 저장 결정 replay. 실제 변경 반영 함수는 기존 엔진 경로를 사용하며 존재하지 않는`resume_admission` API를 가정하지 않는다.

### 4.2 backend 준비 상태와 대체 규칙

- 기존 READY handshake·bounded restart/backoff·세대별worker ID를 조사하고 미준비 실행의 원인을 재현한다.
- 준비 성공/실패·import/worker 오류·재시작·메모리/시간 제한을 구분한다. 재시작 상한을 무제한으로 늘려 성공을 만들지 않는다.
- dispatch와 auxiliary별 요청 수, RH 입력 생성 수, solver 호출/반환 수, 유효 계획 수, primary 반영 수, fallback 수를 기록한다. 하나의 요청에서 호출이 여러 번일 수 있어 각 분모를 명시한다.
- solver 반환0회인 실행도 원래 운영 결과·분모에 남긴다. 별도 분석 필드`solver_exposure`로 퇴화 운영 여부를 표시한다. 기존 엔진의 SUCCESS/FAILED를 임의로 덮어쓰지 않는다.
- 의도적 fallback 회귀와 성능 평가를 구분한다. 전량fallback 실행은 해당 결합 정책의 기록이며 solver 자체 우세의 증거로 사용하지 않는다.

### 4.3 G0 완료 기준

| 검사 | 완료 기준 |
|---|---|
| 공통 제어 반례 | 위 정상·실패 경로 회귀 모두 통과. 통로 변경이 예외로 중단되지 않음 |
| 물리/작업 장부 | 중복 배정·작업 유실·불법 점유·고아 예약0, 보존식 통과 |
| 에너지 장부 | 현재 계약의 허용오차로 검증하고 초기/잔여/소비/충전/구조를 모두 보존 |
| 제때 반영 | 기한 초과 primary 수락0, publication coverage 위반0인 기술 canary |
| backend 노출 | 실제 지원 canary에서 RH별 유효 반환·primary 반영을 확인. 상시미준비 원인 미해결이면 G0 미통과 |
| 재현성 | 정상·통로 변경·미준비/fallback 경로의 저장 결정 재생 일치 |
| 버전 | 새 source·commit·설정·환경과 수정 전 실패 증거를 함께 기록 |

G0는 최종 공장 안전 인증이나 모든 입력의 지원을 뜻하지 않는다. 확인한 범위를 명시한다. 새 입력의 지원 여부는 M1에서 다시 검사한다.

## 5. M1 — 실행 입력·관측창·예산 검수

### 5.1 현재 지원과 추가할 부분

|`run_suite`, study 동결·실행·집계 | 상태·hash·실패 분모·압축·재생 | 새18조건과복수지도 manifest의 실행/재개·진행표 연결 검수 |

| frozen snapshot benchmark | 같은 모델의 두 backend 비교 | 반환된 관측의 선택 편향 명시, 미반환 입력 보존은 별도 확장 |

기존`materialize_korean_case_pilot.py`는 지정된 schema·parameters를 검사한다. 새 초안을 기존`design.json`에 덮어쓰거나 임의의새필드를 추가한 뒤 곧바로 실행하지 않는다. 신규 파일명과CLI는 구현 단계에서 확정하며 현재 지원하는 명령처럼 문서화하지 않는다.

### 5.2 입력 생성 계약

- 새 수요seed5개를 예약한다:`2026111901`~`2026111905`. 번호 예약만으로 입력 생성·검수가 완료된 것은 아니다.
- calibration/canary는`2026111900`으로 분리한다. 지도 validation은 지도별5개씩 다른 seed를 사용한다: CORRIDOR는`2026111911`~`2026111915`, BYPASS는`2026111921`~`2026111925`, STATION은`2026111931`~`2026111935`. 선택적 장기 검증은`2026111941`~`2026111943`이다. heldout seed와 지도는 확인 실험 등록 시 별도 확정한다.
- 난수 흐름을 도착·작업속성·초기SOC·처리잡음 등으로 분리한다. 정책이 실행된 순서가 외부 입력을 바꾸지 않게 한다.
- 같은 load/seed에서 smooth와burst는 실제 작업수·UID·목적지·우선순위·처리잡음을 보존하고 도착시각과 같은 상대 납기만 변환한다. warmup 도착은 기존 변환 규칙을 유지한다.
- 충전 슬롯 변경 시 trace·배터리용량·슬롯당속도·초기SOC·위치를 고정한다.
- 부하 수준이 다르면 실제 작업수와 UID 집단도 달라질 수 있다. 같은 작업집단이라고 주장하지 않으며 정책 비교는 같은condition 안에서 pairing한다.
- 모든 계획 입력에 단위·schema·layout/trace/설정/content hash를 기록한다. 예약ID 변경·지도 축척만으로 독립 지도를 만든 것으로 세지 않는다.
- burst가 입력창 밖으로 작업을 잃거나 미기록으로 삭제하지 않도록 UID·실현 작업수·납기 여유 보존을 검사한다.

### 5.3 관측창과 충전 순환

M2의 초기 후보는 기존과 같은 총2100초·warmup300초·측정1800초다. 이것은 **유한35분 운영 비교**이며 정상상태나 장기 에너지 절약을 자동으로 뜻하지 않는다.

G1 전에 대표 저/고부하·슬롯1/4에서 작업·이동·충전·잔여SOC 궤적을 확인한다. 필요하면 공통3900초/준비300초 또는7500초/준비900초 등의 더 긴 창으로 **전체 M2 설계를 새 버전으로 수정하고 동결**한다. 특정 정책만 더 길게 관측하거나 결과를 본 뒤 유리한 창을 골라 합치지 않는다.

초기2100초를 유지하는 경우 장기 에너지 확인은 별도 묶음으로 둔다. 제안은 저부하·고른도착/4슬롯과 고부하·급증/1슬롯,2조건×새 validation seed3개×4정책=24회, 총7500초·warmup900초다. 이24회는 M2 또는 M3 분모에 합치지 않는 추가 개발 검증이며 필요 시에만 실행한다. 충전하지 않는 저부하도 유효한 대조군이다. 충전 경쟁 조건은 실제 충전 점유·대기·소비가 발생했는지 따로 확인한다.

### 5.4 canary와 실행 예산

G0 후 고정된 새 소스로 아래 검사를 수행한다. 기술 검사의 원시 결과·seed는 개발360회와 구분한다.

| 기술 입력 | 목적 |
|---|---|
| 저부하·4슬롯·smooth | 차이가 작아야 할 대조와 지표 검수 |
| 기준부하·2슬롯·burst4 | 중간 경쟁과 노출 확인 |
| 고부하·1슬롯·burst4 | 계산/충전/미완료 스트레스 |
| 기존 통로 제한을 재생성한 입력 | 변경 중 관측·배정·충전 회귀 |
| 기존3층 분산 충전을 재생성한 입력 | CP-SAT 준비·실제 반환 검수 |

계획량은5입력×4정책=20회 D1 canary다. D0는 대표 저부하·고부하2입력×4정책=8회로 기전/지표를 확인한다. 이28회는 실패 복구를 위한 임의 재시도 예산이 아니다. 소스를 수정하면 새검수묶음ID로 기록한다.

기존 한국 사례 실행기의900초/3600초(run/job) 한도를 출발 후보로 사용하되, 새 관측창과 canary의 실측 비용·저장공간으로 전체 자원 예산을 산정한다. 결정 deadline2초와 실험 run/job 한도는 다른 값이다. 시간 한도를 늘려야 하면 실행 전에 전체 대상에 공통 적용하고 새 설정hash를 동결한다. 이전288회의 벽시계시간만으로 새 실험 완료시각을 보장하지 않는다.

### 5.5 G1 완료 기준

90개 예정 입력·360개 정책 실행의 유일키/순서가 manifest에 존재하고, 도달성·입력축·공통trace·SOC·설정·예정분모 감사가 통과해야 한다. 더 긴 창을 선택해도 조건·seed 수는 같고 입력hash는 달라진다.

canary의 예상 밖 callback 예외·미기록 작업·source 변경·publication coverage 위반·상시 backend 미준비가 있으면 실행 준비상태를 유지하지 않는다. 의도한 제약/solver 실패는 명시적으로 기록하고 회복검사를 통과해야 한다. CPU·메모리·디스크·호스트 잠금·checkpoint·원시 압축 검수 및 저장 결정 재생을 확인한다. 이 문서와JSON의 상태를 수동으로READY로 바꾸는 것이 완료증거를 대신하지 않는다.

### 6.4 실행과 중단 규칙

- M2a: A1의9조건×5seed×4정책=180회. M2b: A4의9조건에서 동일하게180회.
- 각 단계의 전체 순서를 실행 전에 고정하고 정책 순서를 입력묶음 간 균형화한다. 같은 호스트에서 D1 실행을 직렬로 진행하고 다른 solver 실험을 겹치지 않는다.
- M2a/M2b 순서는 개발 단계의 운영 편의다. 두 단계 사이 소스·설정을 바꾸면 같은360회 캠페인으로 합치지 않고 새 설계/캠페인으로 분리한다.
- 작업 실패·timeout·coverage 위반은 그대로 기록한다. 유리한 결과가 나왔다는 이유로 조기 종료하지 않는다.
- 디스크 부족·hash 불일치·예상 밖 제어 예외·장부 불일치는 후속 예약 실행을 정지하고 이미 생성된 결과와 미실행 분모를 보존한다. 정책의 정상적인 solver timeout과 안전 fallback은 실험 전체의 자동 중단 사유로 삼지 않는다.
- 재개는 입력과 코드가 같은 미실행 arm만 대상으로 한다. 완료/실패 arm을 덮어쓰거나 성공할 때까지 재실행하지 않는다.
- 새 버그 수정은 새 source/campaign으로 분리한다. 원본실패·중단시각·수정이유·새예정분모를 함께 공개한다.

### 6.5 G2 완료 기준

360/360 예정 상태를 확인하고, 완료·실패·미실행을 구분해 집계한다. 정상 또는 실패로 실제 종료된360회 기록이 있을 때 실행단계 종료로 표시하고, 미실행이 있으면PARTIAL로 남긴다. “실행 종료”와 “모두 정상”을 구분한다. 정상쌍만의 수치와 실패 포함 전체분모를 함께 제시하고 불완전조건의 추론은 보류한다. 변수 하나 또는 조합을 바꿨을 때 병목 노출이 실제로 변했는지도 보고한다.

좋은 조건뿐 아니라 고른 저부하·이점이 작은 조건·긴급 납기 손해·계산 지연·전량fallback을 모두 결과표에 남긴다.

## 7. M3 — 독립 구조의 지도와 새 수요 검증

M2에서 본 지도와 수요를 그대로 늘리는 것과 다른 구조에 대한 검증을 구분한다. 3개의 새 지도에 지도별로 서로 다른 validation seed5개씩을 사용한다.

| 지도 ID 초안 | 구조 | 검수할 특징 |
|---|---|---|
|VAL_CORRIDOR_A|주요 목적지가 공유 좁은 통로를 통과|지정 자원의 점유·대기와 부하 증가 효과|
|VAL_BYPASS_A|주 통로 외에 연결 가능한 경로 존재|도달성·실제 경로거리·자원 노출|
|VAL_STATION_A|서비스 위치/접근이 한 구역에 집중|설비와 통로 중 실제 병목이 무엇인지|

독립지도는 단순한ID 변경·축척 변경·좌표 이동·같은지도 수요seed 변경으로 만들지 않는다. topology·서비스 배치·공유 자원 구조를 명시한다. geometry hash가 다른 것은 필요 검사이며 구조적 다양성을 충분히 증명하지는 않는다.

초기에는8로봇·6설비·60unit 배터리·슬롯당0.25unit/s 등 M2와 같은 설정을 유지한다. 지도 간 이동거리·자원 노출은 달라질 수 있으므로 “지도 구조 하나의 순수 효과”로 단정하지 않고 각 지도 안에서 정책을 pairing한다. 출발 위치·목적지 mapping과 실제 수평 거리를 공개한다.

현재 공통 경로후보K=1을 유지한다. 우회로 지도가 있어도 정책이 여러 경로를 선택하는 최적화까지 평가했다고 주장하지 않는다. 그 질문은 공통 경로 후보·실행 검증을 추가한 별도 버전이 필요하다.

M3에는 좋은 결과만 고르지 않도록 다음4조건을 먼저 예약한다.

| 검증조건 | 이유 |
|---|---|
|ADV_L06_C4_A1|여유·이점이 작을 수 있는 대조|
|ADV_L10_C1_A1|급증 없이 충전 경쟁|
|ADV_L13_C1_A4|급증과 충전 부족의 조합|
|ADV_L13_C4_A4|충전이 상대적으로 여유로운 고부하 급증|

계획량은3지도×4조건×5새seed×4정책=240회 D1이다. M2에서 사용한 지도·수요·결과와 구분한다. M3 결과를 보고 모델/가중치를 다시 고쳤다면 M3는 추가 개발자료가 되며 최종 heldout은 새로 남겨야 한다. 이3개의 의도적으로 설계한 지도에서의 성공이 모든 실제 공장으로의 일반화를 뜻하지 않는다.

G3 완료 기준은 예정240회 분모 보존·지도 구조/도달성 감사·공통 입력·실패/반영/자원/에너지 검수와 조건별 재현 여부 보고다. 미실행이 있으면PARTIAL로 남기고 종료된 실패도 정상 관측으로 바꾸지 않는다. 확인 가설이나 후보 선택을 바꿨다면 변경 이력도 남긴다.

|건당 에너지|측정창 소비/측정창 완료 수|완료 작업별 생애 에너지가 아님. 완료0이면null|
|결정 지연|관측/compute/검증/반영·fallback 단계와종단간P50/P95/P99/max|dispatch/auxiliary 분리, 늦은창 deadline 검열, solver 시간과 구분|
|실제 최적화 노출|요청·입력생성·solver호출/반환·유효해·primary반영|분모별 기록. 기다리기 prefix 수락이 작업 완료는 아님|
|fallback|eligible 결정 대비대체규칙비중과사유|stale·all-deferred·검증거절·미준비·timeout 분리|
|후보 제한|pending 수·포함/제외 UID·제외횟수|현재계획제외는작업취소가아니며다음관측에서다시포함가능|
|계산 규모|변수·제약·관측 worker RSS·실행wall·압축/분석비용|worker peak와전체호스트peak 구분, 로그압축은결정지연에합치지않음|

backlog는60초 고정 구간으로 기록하고 측정창 전체 및 사전 지정한 급증 전·중·후 구간의 기울기를 보고한다. 급증변환 규칙으로 정한 시각을 사용하며 각 정책 결과에서 유리한 구간을 고르지 않는다. 미완료가 지속 증가하는지와 처리량 plateau를 함께 보며 도착률배수만으로 과부하를 확정하지 않는다.

burst/조건 간 납기는 측정경계 때문에 집단이 달라질 수 있다. 각 정책 비교는 동일condition의 due UID hash를 검증하고, 조건 간 비교에는 공통 UID 집단과 전체집단 결과를 병기한다. 최고령 작업·진행 중 대기는 관측된 나이이며 미래 완료까지의 총 대기시간이 아니다.

충전·캐빈·통로의 occupancy가 현재 로그만으로 충분하지 않으면 계측확장을 선행한다. 새 지표를 이미 구현된 것으로 표시하지 않는다. 집계된 메트릭과 원시이벤트 재구성값이 일치해야 한다.

아래는 후속 backlog이며 전부360회에 포함하지 않는다. 각 묶음마다 조건·예산·seed·주지표를 별도로 확정한다.

필요한 경우 RH 배정만/충전만/공동계획의 절제실험으로 원인을 분리한다. 현재 정책의 단순 스위치만으로 의미가 같다고 가정하지 않으며, 물리·목적·시간비용 검수와 별도 구현이 필요하다. 관측만으로 “개선 원인이 충전계획 하나”라고 확정하지 않는다.

## 10. MILP와 CP-SAT의 동일 관측 비교

운영 시뮬레이션은 초반 선택 이후 상태와 재계획 입력이 달라진다. backend 풀이 성능은 같은 snapshot·모델·시작해를 주는 별도시험에서 확인한다.

- 기존`freeze-snapshot`과`benchmark-snapshot` 기능을 활용하고 입력/model hash·목적·제약·힌트 일치를 검증한다.
- 부하/충전상태를 기준으로 관측 선택 규칙을 먼저 정한다. 좋은 결과를 반환한 관측만 골랐으면 해당 조건부 범위를 공개한다.
- timeout/미반환 관측 입력까지 보존하는 기능이 부족하면 별도 구현하고, 그전에는 전체 호출 대표성이나 timeout 분포를 일반화하지 않는다.
- 제안 소규모시험은6관측×2backend×2호출예산(0.5/2초)×기술반복3회=72호출이다. **72개의 독립 수요실험이 아니다.**
- 호출예산과 D1 관측→반영2초 계약은 다르다. build/solve/prepare/IPC·검증 계측범위와 late 반환을 그대로 기록한다.
- 목적값·유효해·bound/gap·최적증명·실패·wall·RSS를 비교한다. 같은 시간 안에 조금 더 좋은 계획을 만드는지와 전체운영 개선을 각각 설명한다.

native CP-SAT 표현은 동일 grid backend 비교에 섞지 않는다. native를 추가하려면 모델 의미·단위·행동공간·동등성·검증·실행·예산을 별도로 등록한다.

## 11. M4 — 확인 실험과 환경별 선택 기준

M2/M3는 개발·검증 자료다. 독립 확인 실험의 seed 수는 paired 차이의 변동·목표 정밀도·최소실용차이·지도별 범위를 이용해 산정한다. “seed5개이므로 통계적으로 충분하다”거나 기술반복을 독립표본으로 세지 않는다.

확인 실행 전에 다음을 동결한다: 가설·주지표·최소실용차이·안전/납기 가드레일·SLA·비교가족·다중검정방법·CI 방법·실패/검열 처리·예정표본수·중단기준·공통예산·선택규칙. 새 heldout 지도/수요는 튜닝에 사용하지 않는다. 자동 선택 규칙 자체의 효과도 heldout에서 평가한다.

### 11.1 실용 기준의 초안

아래 수치는 프로젝트 연구용 제안이며 현장 SLA나 등록 완료 기준이 아니다. M4 등록 시 개발 결과의 변동과 운영 목적을 검토해 최종 확정하고 hash를 잠근다. 채택기준을 바꿨다면 변경전 기준의 결과도 숨기지 않는다.

| 구분 | 초안 기준 | 적용 |
|---|---|---|
|안전/일관성|불법점유·중복작업·미기록유실·기한초과primary수락0|위반한지원범위에운영추천보류|
|시간지원|publication coverage위반0, eligible 결정기한초과율1%이하|실측범위만판정.2초hard보장이라고부르지않음|
|backend지원|설명되지않은전량미준비실행0|기존결과삭제금지. 해당조건의solver기반추천보류|
|처리량개선|paired평균+5%이상이며등록CI/다중검정에서개선근거|긴급/일반작업·시간가드레일과함께판정|
|납기개선|전체또는긴급위반5pp이상감소, 처리량비열등기준-2%|어떤납기를주지표로쓸지미리선택|

|긴급손해방지|휴리스틱대비긴급위반증가2pp이내|등록한paired단측CI로평가하는방안|
|절대서비스|긴급위반10%이하를연구용SLA후보로둠|추론/집계방법까지등록. 충족정책없음도유효한결과|

상대적으로 좋아졌다는 사실만으로 절대서비스 기준을 만족했다고 부르지 않는다. 연구용10%는 실제 공장 권장값이 아니다. 대기·일반작업 기아의 수용기준도 운영목적에 맞춰 M4 전에 등록한다.

paired 단위는 같은 지도·condition·수요seed의 정책쌍이다. 결정수천개를 독립seed로 세지 않는다. 복수지도는 지도별 효과를 먼저 보고하고, 고정된 구조집합의 집계와 실제 공장 모집단 일반화를 구분한다. bootstrap/CI는 지도/seed의 군집구조를 보존한다. 다중비교는 주후보2개와 등록조건에 맞춰 가족을 정하고 Holm 등의 사전등록 방법을 사용한다.

현재 분석기는 지도별 최소10개의 확률적 수요쌍·지도집계 최소3개라는 구현 게이트를 가진다. M2/M3의5seed는 탐색적 기술통계이며 이 게이트를 낮춰 CI를 만들지 않는다. 지도 간 같은 수요seed를 재사용한 집계는 교차군집 방법을 구현·검증하기 전까지 추론을 보류한다. 본 초안의 M3는 지도별 seed를 분리했다. 최종 표본 수는 이 구현 하한과 검정력/정밀도를 모두 검토해 정한다.

불완전한 계획쌍·지원 실패를 숨기거나 실패에0처리량을 대입하지 않는다. 완전한 쌍의 기술통계와 전체 실패분모를 병기하고, 등록된 확인기준이 불충족이면 추론/추천을 보류한다. solver가 실행되지 않은 결합정책 결과는 운영성능으로 보존하되 solver 자체의 우세로 분류하지 않는다.

| 단계 | 선행 조건 | 작업량 초안 | 다음 단계로 넘길 증거 |
|---|---|---|---|
|M0|현재실패기록확보|공통제어/backend분석·수정·회귀|G0 검수·새소스식별자|
|M1|G0통과|90입력생성·감사, D1 canary20+D0 기술8|G1·관측창·예산·실행순서동결|
|M2a|G1통과|9조건×5seed×4정책=180 D1|전체분모·기술통계·계속지원확인|
|M2b|같은소스/설정유지|9조건×5seed×4정책=180 D1|G2·360회전체보고서|
|M3|지도/입력검수완료|3지도×4조건×5새seed×4정책=240 D1|G3·일반화범위/반례|
|장기/동일관측|각각별도등록|선택적장기24운영회 /snapshot72기술호출|에너지/풀이성능의조건부근거|
|M4|분석·표본수·선택규칙등록|예정수아직미확정|독립확인결과·최종선택표|

필수로 수량을 예약한 운영 검사는 M1의28회+M2의360회+M3의240회=628회다. 선택적 장기24회를 포함하면652회다. snapshot72호출과 회귀테스트는 운영 실행수에 합치지 않는다. 기존288회와 이628회를 새 동일실험의 표본으로 합산하지 않는다. M4는 미확정이므로 최종 전체실험수가 확정됐다고 표시하지 않는다.

M1에서 run별CPU/wall·메모리·논리/압축바이트·디스크 여유를 측정해 캠페인 자원예산을 계산한다. 제한으로 미실행이 생기면 분모에 남긴다. 자원이 부족하면 계획을 실행 전에 개정하고, 실행 후 불리한seed를 삭제해 예산을 맞추지 않는다.
