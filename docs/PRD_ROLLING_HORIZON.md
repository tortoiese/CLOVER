## 1. 한 문장 제품 정의

**현재 도착한 작업과 로봇·공유자원의 상태를 바탕으로, 가까운 미래의 이동·작업·충전을 함께 계획하고, 실제 상황 변화에 따라 반복 수정하며, 동일한 문제를 MILP와 CP-SAT으로 풀어 비교할 수 있게 한다.**

12세 수준으로 설명하면: 여러 로봇에게 다음 할 일만 하나씩 나눠주는 것을 넘어, 충전기와 작업장이 겹치지 않는 짧은 시간표를 만들고, 조금 실행한 뒤 새 시간표를 다시 만드는 기능이다. MILP와 CP-SAT은 그 시간표를 계산하는 서로 다른 두 계산기다.

### 1.1 세 개의 개념을 구분한다

- **Rolling Horizon:** 계획 → 일부 실행 → 상태 갱신 → 재계획이라는 운영 방식이다.
- **MILP:** 정수 선택과 선형 제약·비용으로 계획 문제를 표현하고 푸는 방식이다.
- **CP-SAT:** 정수·논리·스케줄링 제약으로 계획 문제를 푸는 다른 방식이다.
- CP-SAT은 MILP 다음에 결과를 보정하는 필수 후처리가 아니다. **같은 컨트롤러에 연결하는 대체 백엔드**다.
- 두 백엔드를 모두 구현했다고 두 결과를 한 로봇에 동시에 실행하지 않는다. 엔진마다 한 정책만 실제 행동을 확정한다.

## 2. 현재 main의 사실과 해결할 문제

### 2.1 확인된 현황

1. 실시간 스케줄러는 `baseline`, `optimized`다. `optimized`는 가중치 휴리스틱이다.
2. 별도 운영안 비교에 `simulation/milp_scheduler.py`의 SciPy/HiGHS 배정 MILP가 있다.
3. 기존 배정 MILP는 현재 유휴 로봇–작업–설비의 조합을 선택한다. 전체 시간표나 충전량을 함께 결정하지 않는다.
4. `simulation/comparison.py`의 독립 실험은 Baseline과 배정 MILP를 비교한다. 가중치 휴리스틱은 별도 대조군으로 포함되지 않는다.
5. 다층·통로·교차점·엘리베이터의 실행 제약은 존재하지만, 그것이 곧 시간대별 자원 예약의 공동 최적화를 뜻하지는 않는다.
6. 실시간 ROI와 운영안 비교 ROI는 전력 추정 방법·단위·비교 정책이 다르다.
7. 실제 main GUI 실행과 전체 테스트 96개 통과 이력이 있다. 이 검수는 macOS/Python 3.14 환경이며 모든 플랫폼이나 모든 물리 조건의 정확성을 증명하지 않는다.

### 2.2 선행 수정이 필요한 검증된 문제

| 문제 | main에서의 재현 | 왜 먼저 수정해야 하는가 |
|---|---|---|
| 핫리로드가 통로 자원을 교체 | 용량 1의 이전 자원에 1대, 새 자원에도 1대 점유 허용 | 잘못된 용량 모델에서 알고리즘의 처리량을 비교하면 결론이 왜곡됨 |
| 통로 폭에 따른 통행 가능성 검사 부족 | 폭 0.2m 통로를 폭 2m 로봇이 통과 | 불가능한 경로가 계획·실행 가능 경로로 취급됨 |

이 두 항목은 최소 재현 검사로 확인한 것이며 일반 GUI 시연에서 실제 충돌 장면을 관찰했다는 뜻은 아니다. 회귀 테스트를 먼저 추가하고 수정해야 한다.

### 2.3 해결할 사용자 문제

- 작업장·충전기에 로봇이 몰려 대기하지만, 배정 시각과 자원 점유가 연결된 설명이 없다.
- “최적화”가 휴리스틱인지 MILP인지, 실시간 결과인지 독립 실험인지 구분하기 어렵다.
- 새로운 알고리즘을 붙일 때마다 스냅샷·예약·실행·지표 코드가 중복될 위험이 있다.
- 후보 제한·시간 제한·계산 실패·부분 계획을 숨기면 사용자가 “전체 최적해”로 오해한다.
- 같은 작업 입력·비용 모델·계산 예산이 아니면 정책 성능을 공정하게 비교할 수 없다.

## 3. 목표·비목표·완료의 의미

### 3.1 제품 목표

| 목표 | 구현 완료를 판단하는 증거 |
|---|---|
| G1. 배정에서 시간표 계획으로 확장 | 한 계획에 이동·대기·작업·부분 충전·종료 배터리가 포함됨 |
| G2. 공유자원 점유를 일관되게 처리 | 계획 예약·실제 SimPy 점유·취소·지연·핫리로드의 회귀 테스트 |
| G3. 백엔드 교체 가능 | 같은 입력·공통 모델·계획 계약으로 MILP와 CP-SAT을 선택 실행 |
| G4. 비교의 공정성과 재현성 확보 | 공통 trace, 정책 ID, 모델 해시, 원시 표본, 버전·예산을 포함한 결과 |
| G5. GUI에서 이해·조작 가능 | 정책·적용 범위·계산 상태·대체 규칙 사용을 사용자에게 표시 |
| G6. 실패해도 시뮬레이터 유지 | 계산 오류·무해·취소·오래된 결과에도 작업 중복이나 UI 정지가 없음 |

### 3.2 이번 요구 범위 밖

- 실제 공장 로봇·PLC·MES에 제어 명령을 송신하거나 실기기 안전 인증을 받는 일.
- 연속 공간의 모든 충돌·제동거리·동역학을 보장하는 완전한 다중 로봇 경로 계획.
- 아직 발생하지 않은 실제 작업이나 처리시간 표본을 미리 보는 예측.
- 로봇·충전소 대수·위치·공장 레이아웃의 자동 설계 및 무인 적용.
- 완제품 다단계 공정 라우팅/BOM/공정 선후행 전체를 새로 구현하는 일. 현재의 작업 1건 의미를 유지한다.
- 실측 데이터 없이 투자 회수나 기업 수익 개선을 보장하는 일.
- MILP 또는 CP-SAT이 모든 조건에서 휴리스틱보다 우수하다는 사전 결론.
- 자연어 입력만으로 목적함수·제약식을 임의 생성해 실행하는 기능.

### 3.3 기능 완료와 효과 입증은 다르다

- **기능 완료:** 모델·실행·실패 처리·GUI·재현 실험이 요구사항과 일치한다.
- **효과 입증:** 사전에 정한 조건에서 강한 대조군과 비교해 개선을 관측했다.
- 기능이 정확해도 성능이 나쁠 수 있다. 이 경우 결과를 공개하고 모델·설정을 조정한다.
- 처리량만으로 판정하지 않는다. 미완료량·대기 꼬리·납기·에너지·실행 지연을 함께 보고한다.

## 4. 단계별 출시 범위와 정책 이름

### 4.1 단계 정의

| 단계 | 주요 범위 | 통과 게이트 |
|---|---|---|
| M0 기반 정비 | 물리 오류 수정, 단위·자원 식별자·trace·공통 지표 계약 | 물리 회귀와 기존 기능 회귀 통과 |
| M1 RH-MILP | 공통 컨트롤러 + 작업장·충전기 시간표 + MILP + 접두 구간 실행 | 작업장·충전기 범위의 모델·실행 검증 |
| M2 RH-CP-SAT | M1과 동등한 공통 모델을 CP-SAT으로 풂 | 작은 문제 최적 목적값 동등성·실행 계약 검증 |
| M3 교통 자원 확장 | 통로·교차점·단일 캐빈 엘리베이터의 시간 점유를 양 백엔드에 반영 | 해당 자원 모델·실행·지연·핫리로드 검증 |
| M4 통합 검수 | GUI·비교·ROI·로그·다중 시드·플랫폼 검증·시연 자료 | 최종 인수 체크리스트 통과 |

M1~M2는 중간 출시다. GUI에 `작업장·충전기 계획 / 교통 자원은 실행 시 제어`라고 표시한다. **통로·엘리베이터까지 공동 최적화했다고 발표하려면 M3가 필수**다. M1~M2의 다층·혼잡 시나리오는 제한적·실험적 지원이며, 정체를 모두 예측하는 모델로 설명하지 않는다.

### 4.2 정책 레지스트리

| 영구 policy_id | GUI 이름 제안 | 용도 |
|---|---|---|
| `baseline_fifo` | Baseline — 순차 배정 | 기존 `baseline`과 연결, 기준선 보존 |
| `weighted_heuristic` | 가중치 휴리스틱 | 기존 `optimized`와 연결, 강한 대조군 |
| `assignment_milp_legacy` | 배정 MILP — 기존 모델 | 현재 SciPy 모델, 기본은 독립 비교용 |
| `rh_milp` | Rolling Horizon MILP | 새 공통 컨트롤러의 MILP 백엔드 |
| `rh_cpsat` | Rolling Horizon CP-SAT | 같은 컨트롤러의 CP-SAT 백엔드 |

- `mode` 기존 저장값과 새 policy_id의 매핑을 두어 기존 DB·명령을 깨지 않는다.
- `backend_id`, `model_version`, `objective_profile`, `planner_scope`, `unit_profile`은 policy_id와 별도로 저장한다.
- 초기 기본 정책은 가중치 휴리스틱을 유지한다. 새 정책은 검증 후 사용자가 선택한다.
- 실시간으로 모든 무거운 백엔드를 무조건 함께 실행하지 않는다. 실행 정책 선택과 화면 선택은 12장에서 분리한다.

## 5. 사용자와 핵심 사용 시나리오

| 사용자 | 요구 | 성공 흐름 |
|---|---|---|
| 팀 개발자 | 같은 문제에서 두 백엔드를 비교 | snapshot/trace 고정 → 백엔드만 변경 → 검증·결과 비교 |
| 발표자·교수 | 병목 완화의 이유를 확인 | 자원별 시간표와 실제 대기, 제약, 비교 조건을 함께 확인 |
| 공장 운영 사용자 | 왜 기다리거나 충전하는지 이해 | 선택 정책·현재 행동·예약 이유·실패/보류 원인 조회 |
| 실험 담당 | 같은 실험 재현·내보내기 | trace·설정·시드·버전·원시 반복 결과 저장 및 재실행 |

### 시나리오 U1: 충전기 병목

로봇 5대·충전 슬롯 1개에서 작업량을 늘린다. RH 정책이 충전 순서·부분 충전량·작업 시작을 결정한다. 사용자는 대기·충전 예약과 실제 점유를 확인한다. 최적해가 없으면 검증된 실행 가능 해 또는 명시적인 대체 규칙으로 이어진다.

### 시나리오 U2: 작업장 대체 배정

같은 작업을 처리할 수 있는 두 설비가 있다. 정책은 가까운 곳뿐 아니라 작업 종료까지의 점유와 다른 작업의 배정 가능성을 고려한다. 단일 설비에 대한 중복 작업 예약은 금지한다.

### 시나리오 U3: 다층·교통 병목

로봇이 좁은 통로와 엘리베이터를 공유한다. M3에서는 시간대별 점유와 캐빈 위치를 포함해 계획한다. M1~M2에서는 해당 교통 제약이 계획에 완전히 포함되지 않는다는 경고와 실제 지연·재계획을 보여준다.

### 시나리오 U4: 긴급 변화

계산 중 주문 취소·긴급 주문·설비 고장·용량 변경·리셋이 발생한다. 이전 결과를 무조건 실행하지 않고, 영향받는 계획을 검증·폐기하며 실제 진행분을 정산한다. 취소된 작업이 대기열에 다시 나타나면 실패다.

## 7. 공통 아키텍처와 변경 범위

### 7.1 구성 원칙

```text
GUI: 정책 선택 / 상태·예약 표시 / 비교 실행
                  │ Qt Signal/Slot
SimWorker / SimulationEngine — 실제 SimPy 상태의 유일한 소유자
                  │ 불변 Snapshot
RollingHorizonController
  ├─ 후보·경로·자원 calendar → 공통 PlanningProblem
  ├─ Solver supervisor → 별도 solver process
  │                      ├─ MILP backend
  │                      └─ CP-SAT backend
  └─ 최신 상태 Validator → ReservationTable → PrefixExecutor
                                             │
                                실제 Robot / Resource / 에너지 계측

ExperimentRunner → 동일 trace를 독립 엔진들에 주입 → Metrics/Economics/Export
RAG → 이미 계산된 결과와 문서 근거만 설명, Plan을 직접 수정하지 않음
```

- 솔버는 DB·QWidget·실제 SimPy Resource·Robot 객체를 읽거나 수정하지 않는다.
- MILP와 CP-SAT은 각각 실행기를 만들지 않는다. 상태 생성·검증·예약·실행·경제성은 공통이다.
- 목적함수·처리시간·에너지 정수화를 각 백엔드가 별도로 해석하지 않는다.
- 계획 수락·예약 반영·작업 제거는 SimWorker에서만 수행한다.
- QThread를 강제 종료해 네이티브 솔버를 끊는 방식을 사용하지 않는다. 강제 종료가 필요하면 격리된 solver process만 대상으로 한다.
- SimWorker의 snapshot 생성은 현재 상태를 짧게 복사하는 작업으로 제한한다. 모든 경로 쌍의 Dijkstra나 전체 모델 생성은 solver process에서 수행하고 topology_version별 캐시를 사용할 수 있다. route adapter·공통 builder 비용도 계산 예산에 포함한다.

## 8. 단위와 공통 최적화 모델

### 8.1 단위 계약 — 두 백엔드가 같은 문제를 풀기 위한 조건

CP-SAT의 제약은 정수로 표현해야 하므로 실수 배터리·시간을 그대로 복사할 수 없다. 이 제약은 [OR-Tools CP-SAT 공식 안내](https://developers.google.com/optimization/cp/cp_solver)에 명시되어 있다.

**권장 결정: M1~M2의 기본 비교 모델은 양 백엔드 모두 동일한 정수 에너지·충전량을 사용한다.** MILP 도구에서 모든 의사결정 변수를 정수로 두는 것은 정수 선형계획 특수 경우다. 기존 연속 충전량 MILP를 참고용으로 유지할 수 있지만 다른 model_version이며 CP-SAT과 같은 가능 영역이라고 주장하지 않는다.

| 항목 | 공통 계약 제안 |
|---|---|
| 시뮬레이션 시간 | 원본은 sim-sec, 계획 변수는 snapshot 시각에 대한 정수 tick |
| 시간 격자 Δ | 기본 1초, 검증 프로필 0.5/1/2초 |
| 계획 구간 H | 기본 60초, 최대 300초. 실제 구간은 N=floor(H/Δ), H_eff=NΔ로 기록 |
| 거리 | 원본 실제 수평 이동거리 m, 정수화 해상도 0.001m |
| 배터리 | 퍼센트가 아닌 로봇별 실제 상대 에너지 단위. ε_B=0.001 단위가 초기 제안 |
| 잔량·용량 | ε_B 단위로 내림해 가용량을 과대평가하지 않음 |
| 최소 예비량 | 실제 배터리 용량의 기본 10%를 ε_B 단위로 올림 |
| 이동·작업 소비 | 전체 행동의 예상 소비를 ε_B 단위로 올림 |
| 충전 최대 증가 | 충전 속도×슬롯 길이를 ε_B 단위로 내림 |
| 비용 계수 | 공통 builder에서 Decimal 기반 고정 배율로 정수화. 초기 배율 10^6 |
| 원화·전력 | 내부 계약 KRW, Wh, 원/kWh. 화면 변환에서만 다른 단위 허용 |

- 행동 소비를 슬롯에 배분할 때 각 슬롯을 무조건 다시 올림하지 않는다. 정수 소비 총합이 행동 소비와 정확히 일치하게 나눠 배분한다.
- 정수화 전후 값·반올림 방향·오차 상한을 로그에 남긴다. 작은 소비가 음수가 되거나 비영 비용이 의도치 않게 0이 되면 검증 실패로 처리한다.
- 최대 계수×변수 상한×항 개수의 합이 64비트 정수 범위를 넘지 않는지 모델 생성 전에 검사한다. 초과 시 입력 오류로 종료하며 조용히 overflow시키지 않는다.
- 정수화 후 가능 영역과 비용 계수 배열이 동일해야 백엔드 동등성 실험으로 인정한다. 해상도가 다르면 별도 실험군이다.
- 배터리 상대 단위와 Wh 환산은 다르다. 로봇 종류별 Wh/배터리단위가 다르면 로봇별 값을 사용한다. 알 수 없으면 실제 전력 비용을 미산정으로 둔다.

### 8.2 계획 대상과 행동 그래프

- 집합 R: 이번 계산에서 자유롭게 계획할 수 있는 로봇. M1~M2는 현재 유휴 로봇만 포함한다.
- 집합 J: 현재 접수되어 미배정 상태인 후보 작업. 기본 최대 8개, 고급 설정 최대 32개를 제안한다.
- 집합 Q: 이번 planner_scope에서 계획하는 공유자원.
- 각 로봇의 행동 a는 `(출발 위치·층, 시작 tick) → (도착 위치·층, 종료 tick)` 연결이다.
- 행동 종류는 move, wait, work, charge, end다. M3에서는 이동의 구간별 자원 사용과 엘리베이터 캐빈 행동도 포함한다.
- 작업장·충전소의 진입 위치·층과 실제 노드/경로를 보존한다. 같은 x,y라도 층이 다르면 다른 위치다.
- 허용되지 않은 설비·로봇 전용 주문 위반·통과 불가능한 폭·끊긴 경로·도달 불가 충전소를 사용한 행동은 만들지 않는다.

후보는 우선순위·aging·납기·생성 시각으로 결정적으로 정렬한다. 후보 밖 작업은 큐에 그대로 남기고 별도 수로 보고한다. 신규 작업이 많다는 이유로 기존 작업을 지우지 않는다. 긴급 작업의 후보 포함 규칙과 오래된 작업의 포함 주기를 테스트한다.

작업이 계획 구간보다 길어 행동을 만들 수 없는 경우를 구별한다. 가능하면 공통 설정으로 H를 상한 내 확장하고 이를 기록한다. 상한보다 긴 작업은 `HORIZON_TOO_SHORT`를 표시하고 검증된 장기 작업용 safe-prefix fallback 또는 명시적 정책 지원 불가로 처리한다. 무한히 조용히 보류하지 않는다. safe-prefix는 전체 구간 계획과 다른 plan_type이며 최적해로 표시하지 않는다.

장기 작업의 권장 기본 동작은 충전소 도달 에너지·허용 설비·자원 점유를 검증한 단일 safe-prefix 실행이다. 예약은 H 밖의 작업 종료까지 보존한다. 이것을 검증할 수 없을 때만 지원 불가/안전 대기로 전환하고 사용자에게 조치를 안내한다. 이 동작은 ADR-09에서 확정한다.

### 8.3 변수와 기호

| 기호 | 의미 |
|---|---|
| x_ra ∈ {0,1} | 로봇 r이 행동 a를 선택 |
| f_i ∈ {0,1} | 후보 작업 i를 이번 계획 구간에서 완료하지 않고 보류 |
| B_rτ ∈ Z≥0 | tick τ에서의 배터리, ε_B 단위 |
| g_ra ∈ Z≥0 | 충전 행동의 증가량, ε_B 단위 |
| s_a, e_a | 행동의 미리 정해진 시작·종료 tick |
| h_aqτ ≥ 0 | 행동 a가 자원 q의 tick τ에 요구하는 슬롯/차선 수 |
| F_qτ ≥ 0 | 이미 확정되었거나 실제 진행 중인 자원의 고정 사용량 |
| C_qτ ≥ 0 | 자원의 명목 가용 용량 |
| c_i, D_i | 작업 생성 시각·납기, 절대 sim-sec. 납기 없음은 별도 값 |
| y_rℓ | 위치 ℓ에서 끝나는 end 행동의 선택값. 별도 자유 변수로 중복 정의하지 않아도 됨 |

### 8.4 목적함수: 두 단계

#### 1단계: 가중 보류 비용 최소화

\[
\min F_1=\sum_{i\in J} w_i f_i
\]

초기 제안 가중치:

\[
w_i=p_i+\left\lfloor\frac{\max(0,t_0-c_i)}{30}\right\rfloor,
\quad p_i\in\{8,4,2,1\}.
\]

긴급·높음·보통·낮음에 각각 8·4·2·1을 준다. 이는 가중치 절충이지 긴급 작업의 절대 우선 처리 보장은 아니다. 절대 우선순위가 필요하면 별도 objective_profile과 단계별 목적을 승인해야 한다.

모든 후보 가중치가 1이면 후보의 구간 내 완료 수를 늘리는 것과 동치다. 우선순위 가중치·후보 제한·고정 행동이 있는 현재 제안은 GUI의 슬라이딩 throughput 자체를 직접 최대화하는 식과 다르다.

#### 2단계: 대기·납기 지연·이동·충전 비용 최소화

작업 i의 work 행동 a에 대해:

\[
W_{ia}=t_0+\Delta s_a-c_i,
\qquad L_{ia}=\max(0,t_0+\Delta e_a-D_i).
\]

납기가 없으면 L_ia=0이다. 초기 비용 프로필의 원래 물리량 기준 표현은:

\[
\begin{aligned}
F_2={}&\sum_{r,i}\sum_{a\in A^{work}_{ri}}
\frac{W_{ia}+5L_{ia}}{H_{eff}}x_{ra}\\
&+0.01\sum_{r,a\in A^{move}_r}d_a x_{ra}\\
&+0.01\Delta\sum_{r,a\in A^{charge}_r}x_{ra}
+0.001\,\varepsilon_B\sum_{r,a\in A^{charge}_r}g_{ra}.
\end{aligned}
\]

비교용으로 실제 푸는 식은 위 항의 계수를 공통으로 정수화한 F_2_int다. 두 백엔드 모두 F_2_int를 최소화한다. 납기는 이 프로필에서 soft penalty이며, hard deadline 보장은 하지 않는다. 계수는 초기 제안이며 실험 전 확정·버전 관리한다.

주문 납기를 개별 작업의 D_i로 사용하면 이는 작업 단위의 납기 proxy다. 모든 주문 잔량·공정의 최종 완료시각을 직접 최적화하는 주문 전체 납기 모델이라고 설명하지 않는다.

- 1단계가 증명된 최적이면 `F1 = F1*`를 고정하고 2단계를 푼다.
- 1단계가 시간 제한의 실행 가능 해이면 `F1 ≤ incumbent_F1` 아래에서 2단계를 풀 수 있다. 이 경우 엄밀한 사전식 전체 최적성은 주장하지 않는다.
- 2단계가 실패하거나 해를 못 찾으면 검증된 1단계 해를 보존한다.
- 1단계만 최적인 결과나 시간 이동된 실행 계획을 전체 최적해라고 표시하지 않는다.
- 두 단계의 시간·목적값·최선 경계는 따로 기록한다. 서로 다른 단계의 gap을 하나의 전체 성능 보장으로 합치지 않는다.

### 8.5 공통 제약식

#### C1. 로봇 흐름 보존

\[
\sum_{a\in\delta^+(v)}x_{ra}-\sum_{a\in\delta^-(v)}x_{ra}=b_{rv},
\]

b는 시작 노드에서 1, 종료 sink에서 -1, 나머지 0이다. 로봇별 연속된 경로 하나를 만들며 동시에 두 행동을 수행하지 못하게 한다. end 연결은 계획 종료를 표현하는 논리 연결이지 실제 이동이 아니다.

#### C2. 작업은 한 번 수행하거나 보류

\[
\sum_r\sum_{a\in A^{work}_{ri}}x_{ra}+f_i=1.
\]

단일 작업의 work 행동은 처리 구간 전체를 점유한다. 일반 재계획은 시작된 작업을 임의로 분할하지 않는다. 다단계 제품 공정 선후행은 별도 향후 범위다.

#### C3. 공유자원 잔여 용량

\[
\sum_r\sum_a h_{aq\tau}x_{ra}\le R_{q\tau},
\quad R_{q\tau}=\max(0,C_{q\tau}-F_{q\tau}).
\]

정상 상태에서는 고정 점유와 새 점유의 합이 용량 이하다. 용량 축소로 기존 사용자 F가 명목 용량 C보다 많을 때는 신규 진입을 0으로 제한하고 기존 사용자를 drain한다. 이를 정상 용량 충족으로 숨기지 않고 `grandfathered_usage`로 표시한다. 단순히 F+x≤C만 추가해 모든 계산을 무해로 만드는 것은 피한다.

- 구간은 [start,end)로 정의하며 같은 시각에는 해제를 먼저 처리한다.
- 하나의 실제 점유를 고정 예약과 라이브 상태에서 두 번 세지 않는다.
- work의 모든 점유 슬롯, charge의 모든 점유 슬롯을 포함한다. 시작 시각만 검사하지 않는다.
- M1~M2의 Q는 작업장·충전기다. M3에서는 경로 구간의 통로·교차점·엘리베이터 수요가 추가된다.

#### C4. 배터리 보존·충전 상한

\[
B_{r,\tau+1}=B_{r\tau}-\sum_a e_{ra\tau}x_{ra}
+\sum_{a\in A^{charge}_r:s_a=\tau}g_{ra},
\]

\[
B_{r,ready_r}=B_r^0,
\quad B_r^{reserve}\le B_{r\tau}\le B_r^{capacity},
\]

\[
0\le g_{ra}\le
\left\lfloor\frac{\rho_{q(a)}\Delta}{\varepsilon_B}\right\rfloor x_{ra}.
\]

e_raτ는 공통 builder가 배분한 정수 소비다. 거리 에너지와 작업 에너지를 사용하고, 작업 점유 시간을 격자에 맞춰 올린 보수적 기간으로 작업 소비를 계산하는 것을 제안한다. 실제 구현 시 이 의미를 energy_model_version에 고정한다.

초기 모델의 소비량 정의는 다음과 같이 고정한다:

\[
\hat p_q=\max(0.5,\mu_q+\kappa\sigma_q),\quad
n_q=\left\lceil\hat p_q/\Delta\right\rceil,
\]

\[
E^{move}_{ra}=\left\lceil\beta_r d_a/\varepsilon_B\right\rceil,
\qquad E^{work}_{ra}=\left\lceil\gamma n_q\Delta/\varepsilon_B\right\rceil.
\]

여기서 거리 d_a는 실제 수평 이동거리이며 엘리베이터 시간 환산 거리와 다르다. M3에서는 구간별 소비 채널을 합산한다. 전체 정수 소비와 슬롯별 e_raτ의 합은 일치해야 한다.

대기 전력·엘리베이터 설비 전력·로봇 충전 손실은 별도 채널이다. 초기 로봇 대기 소비를 0으로 가정하면 그 사실을 결과에 표시한다. 예상 처리시간은 기본 평균+표준편차 1배이며 확률적 방전·지연을 완전히 보장하는 chance constraint는 아니다.

#### C5. 종료 후 충전소 도달 에너지

\[
B_{rN}\ge B_r^{reserve}+\sum_\ell E^{return}_{r\ell}y_{r\ell}.
\]

복귀 에너지는 실제 통행 가능한 층·폭·경로로 계산한다. 이는 도달 에너지 조건이지 충전소가 즉시 비어 있거나 미래 고장이 없다는 보장은 아니다.

복귀 항도 B와 같은 ε_B 단위의 정수다. 초기 이동 소비 모델에서는 `ceil(가장 적은 복귀 이동 에너지 / ε_B)`를 사용한다. 충전소가 현재 위치와 같은 접근 위치에 있으면 이동 소비는 0이다.

기본 `terminal_return_policy=require_reachable_charger`에서는 도달 가능한 활성 충전소가 없는 종료 위치를 허용하지 않는다. 활성 충전소가 전혀 없으면 명시적 원인을 보고하고 안전 대기/복구로 처리한다. 실험적 `reserve_only`를 허용할 경우 별도 모델 hash와 경고를 사용하며 복귀 보장을 주장하지 않는다.

## 9. MILP·CP-SAT 백엔드 상세 요구

### 9.1 MILP 백엔드

- 권장 도구: OR-Tools MPSolver/SCIP. main의 SciPy/HiGHS 배정 모델은 별도 legacy 정책으로 유지한다.
- 공통 행동·점유·에너지·비용 명세를 선형 변수와 제약으로 변환한다.
- 시간 확장 그래프의 고정 시각 행동을 우선 사용해 불필요한 Big-M 충돌 제약을 줄인다.
- M1 비교 모델의 B,g는 정수다. 연속 충전 변형을 추가하려면 별도 명세·테스트·모델 ID를 둔다.
- warm start/greedy hint를 제공할 수 있지만 힌트에 맞추기 위해 목적함수를 바꾸거나 다른 행동을 제거하지 않는다.
- incumbent와 bound가 없을 때 0이나 무한한 gap을 정상 수치로 만들어 표시하지 않는다.
- 동등성 검수에서는 두 백엔드의 상대/절대 gap 조기 종료를 0으로 둔다. 허용 gap을 사용한 운영 프로필은 tolerance를 기록하며 엄밀한 최적성 증명과 구분해 `FEASIBLE_WITH_GAP` 등으로 표시한다. MILP 정수 변수는 허용 오차 안에서만 정수화하고 전체 해를 다시 검사한다.

정수/혼합 정수 모델과 백엔드의 구분은 [OR-Tools MIP 안내](https://developers.google.com/optimization/mip/mip_example), 기존 main의 SciPy 상태·반환값은 [SciPy milp 공식 문서](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.milp.html)를 기준으로 어댑터에서 정규화한다.

### 9.2 CP-SAT 백엔드

- M2의 1차 구현은 같은 PlanningProblem의 x,f,B,g와 동일 정수 선형 제약을 CP-SAT으로 옮긴다.
- 처음부터 다른 후보·배터리 해상도·목적함수의 네이티브 스케줄링 모델로 바꾸지 않는다. 먼저 의미 동등성을 확보한다.
- 고정 시작·종료 행동마다 x를 presence로 하는 optional interval을 만들 수 있다.
- 단일 용량 자원에는 NoOverlap, 다중 슬롯에는 Cumulative를 추가할 수 있다. 공통 시간 슬롯 제약과 같은 가능 영역을 유지하는 중복 제약/표현 변환이어야 한다.
- 자원 용량이 시간에 따라 달라지면 고정 용량 Cumulative 하나로 대체하지 않는다. calendar 차감·차단 interval 또는 공통 슬롯 제약을 유지한다.
- 로봇 이동·층 연속성은 NoOverlap만으로 보장되지 않으므로 흐름/경로 제약을 유지한다.
- hint, seed, 탐색 worker 수를 명시한다. 공정한 기준 실험은 MILP·CP-SAT 모두 단일 worker로 한다.
- 가변 시작 시각 네이티브 interval 모델은 P2 고급 변형이다. 추가 시 `native_interval` 모델 ID와 별도 검증으로 성능 개선을 평가한다.

interval과 NoOverlap을 사용하는 스케줄링 구성은 [공식 Job Shop 예제](https://developers.google.com/optimization/scheduling/job_shop), optional interval·Cumulative 등 API는 [CpModel 공식 참조](https://or-tools.github.io/docs/python/classortools_1_1sat_1_1python_1_1cp__model_1_1CpModel.html)를 따른다. 특정 솔버가 본 프로젝트에서도 더 빠르다고 사전 가정하지 않는다.

### 9.3 상태 계약

| 정규화 상태 | 의미 | 실행 가능 계획 사용 |
|---|---|---|
| OPTIMAL | 요구된 두 단계 모두 해당 snapshot·공통 모델에서 최적성 증명 | 독립 검증 후 가능 |
| FEASIBLE | 검증 가능한 incumbent 존재, 전체 최적성 미증명 | 독립 검증 후 가능 |
| INFEASIBLE | 해당 모델에서 불가능함을 증명 | 새 해 없음, 원인 기록 후 대체 규칙 |
| UNKNOWN / NOT_SOLVED | 제한 등으로 증명·사용 가능한 해 없음 | 불가능으로 단정하지 않음 |
| MODEL_INVALID | 단위·범위·직렬화·모델 오류 | 실행 금지, 오류 보고 |
| CANCELLED / ERROR / TIMEOUT | 취소·예외·감시 종료 | 부분 변수를 계획으로 해석하지 않음 |

원래 솔버 상태와 정규화 상태를 함께 보존한다. FEASIBLE을 OPTIMAL로, UNKNOWN을 INFEASIBLE로 바꾸지 않는다. [CP-SAT의 공식 상태 의미](https://developers.google.com/optimization/cp/cp_solver)를 준수한다.

2단계에서 1단계보다 작은 보류 비용을 발견한 경우도 최종 계획의 F1을 다시 계산한다. 단계 종료 시의 incumbent와 최종 계획의 실제 목적값을 별도 필드로 기록해 보고서와 적용 계획이 불일치하지 않게 한다.

`solve_status`와 `acceptance_status`는 분리한다. 예: 원래 solve가 OPTIMAL이어도 시간 이동 후에는 `ACCEPTED_SHIFTED_FEASIBLE`이며 현재 상태의 최적해라는 뜻이 아니다. 일부 접두 구간만 적용되면 적용 비율과 나머지 사유도 기록한다.

### 9.4 시간 예산·취소

- 기본 soft 예산 제안: 모델 생성+두 단계 solve 합계 2 wall-sec.
- 1단계에 남은 solve 예산의 약 40%를 우선 배분하고, 2단계는 남은 예산을 사용한다. 비율은 설정·버전 관리한다.
- 워밍된 solver process의 요청 시작 이후 hard watchdog 제안: 3 wall-sec. solver 자체 time limit과 별개다.
- snapshot 생성·queue 대기·모델 생성·각 solve·IPC·검증·적용을 분리 계측한다. end-to-end 지연을 solver 시간으로 축소 보고하지 않는다.
- 과도한 후보·arc·제약 수는 solve 전에 거부한다. 기본 arc 상한은 60,000을 시작값으로 제안한다.
- superseded 요청은 새 요청에 앞서 취소 또는 폐기한다. 엔진당 in-flight 요청은 1개, 대기 요청은 최신 1개만 유지한다.
- solver process가 멈추면 supervisor가 종료·회수하고 다시 준비한다. 메인 GUI·SimWorker는 계속 동작한다.
- 리셋·앱 종료·정책 비활성화는 취소 token을 전달하고, 제한된 종료 시간 안에 자식을 회수한다. 살아 있는 QThread나 자식 프로세스를 남기지 않는다.
- cold process 준비시간도 별도 기록한다. 프로세스 재시작 비용을 숨긴 상태로 실시간 성능을 발표하지 않는다.
- process 초기 준비에도 별도 상한(초기 제안 10 wall-sec)을 둔다. 준비 실패는 backend unavailable로 표시하고 앱·시뮬레이션을 멈추지 않는다.

## 10. 물리 자원과 다층 확장

### 10.1 자원 식별·핫리로드

- `config_version`, `topology_version`, `resource_version`을 구분한다. 공장 이름 변경을 경로·점유 전체 초기화로 처리하지 않는다.
- 변경 없는 자원은 동일한 런타임 자원 객체와 예약을 재사용한다.
- ID가 저장 과정에서 재발급될 수 있다면 안정적인 resource_uid 또는 명시적인 이전→새 논리 ID 매핑이 필요하다. 같은 물리 통로가 서로 다른 자원으로 중복 생성되면 실패다.
- 용량 감소는 기존 사용자를 유지하며 신규 진입을 중지하는 drain 절차로 처리한다. 증가는 대기 요청을 새 용량만큼 허용한다.
- 자원 제거·이동은 사용 중 행동을 안전한 경계까지 마무리하거나 중단 프로토콜로 정산한 뒤 반영한다. 사용자가 있는데 예약만 삭제하지 않는다.
- schema 변경이 필요하면 schema.sql·DBManager 마이그레이션·저장/복원·검증을 함께 변경한다. 기존 DB를 보존하고 명시적으로 버전 업한다.

### 10.2 통로 폭과 차선

- 물리 통과 가능성 검사와 동시 점유 차선 수 계산을 분리한다.
- `edge_clearance`가 벽 양쪽 여유의 합인지, `side_clearance`가 로봇 사이 간격인지 의미·단위를 ADR로 확정한다. 중복 차감하지 않는다.
- 통과 가능성은 원래 폭과 로봇 폭·필요 여유로 먼저 판정한다. 필요한 차선 수를 min(need,capacity)로 잘라 통행을 허용하지 않는다.
- 용량 0인 통로는 논리적으로 사용 불가다. SimPy Resource(capacity=0)를 만들지 않고 경로에서 제외한다.
- 양방향 단차선은 동일한 논리 자원을 사용한다. 방향별로 별도 Resource를 만들어 정면 동시 진입을 허용하지 않는다.
- 여러 차선의 획득은 부분 점유 교착을 만들지 않는 원자적 admission 또는 동등한 규칙으로 처리한다.

### 10.3 거리·시간·에너지 분리

현재 Route의 엘리베이터 가중치는 시간 환산 비용을 포함할 수 있다. 이를 실제 수평 이동거리처럼 에너지·ROI에 곱하지 않는다.

RouteAdapter는 최소 다음을 반환해야 한다:

- 실제 수평 이동거리와 해당 로봇의 이동 에너지.
- 수평 주행시간, 교차점 통과시간, 승강기 공차 호출·문·적재 이동시간.
- 구간별 출발·도착 층, 노드, 자원, 점유 수요.
- 대기 가능한 논리 위치/영역과 대기 중 자원 점유 의미.

### 10.4 M3 교통 자원 계획

- 이동은 단순한 출발·도착 시각뿐 아니라 내부 구간의 자원 점유를 갖는다.
- 초기 M3는 고정 경로의 출발 시각 조정과 구간별 예약을 우선한다. 중간 대기가 필요하면 명시적인 대기 노드/행동으로 모델링하며 경로 도중 임의 시간을 추가하지 않는다.
- 경로 선택 후보를 여러 개 허용하면 양 백엔드가 같은 경로 집합을 사용한다. K개 대체 경로는 후속 고급 옵션이며 기본 K=1로 시작한다.
- 교차점은 진입 전 점유 허가를 받아 통과·해제한다. 이미 교차점 좌표에 들어온 뒤 대기하는 방식으로 물리 점유를 설명하지 않는다.
- 대기 위치·노드 용량·자원 인계 규칙을 모델과 실행기가 공유한다. 모델 밖 무한 대기 공간을 실제 안전 공간으로 오해하지 않도록 표시한다.
- 이 범위의 자원 충돌 방지는 연속 공간 전체의 충돌-free 인증과 다르다.

### 10.5 엘리베이터는 단순 슬롯 자원이 아니다

하나의 캐빈은 현재 층과 이전 운행의 도착 층에 따라 다음 호출 시간이 달라진다. NoOverlap 또는 capacity 제약 하나만 추가해 캐빈 위치가 일관된다고 주장하면 안 된다.

- M3 1차 지원은 **캐빈 1대·동시 운행 1개**로 제한한다.
- 공통 모델에 캐빈의 `(층,tick)` 상태와 wait/empty_move/loaded_trip 경로를 둔다. 로봇의 ride 선택과 해당 캐빈 운행 선택을 연결한다.
- 탑승층까지의 공차 이동, 승차 문, 층간 이동, 하차 문을 시간과 자원 점유에 포함한다.
- 초기 진행 중 운행은 고정 prefix로 넣고 캐빈 위치를 임의로 초기화하지 않는다.
- 취소·설정 변경 중에는 정해진 안전 도착 경계까지 이동하고 정산한다. 즉시 목적 층으로 순간이동시키지 않는다.
- capacity>1의 공동 탑승·배차는 별도 기능이다. 일관된 배치 탑승 모델이 없으면 새 RH 정책에서 지원 불가로 명시한다. 한 캐빈이 동시에 다른 층으로 두 운행을 하는 근사로 대체하지 않는다.

### 10.6 교착·긴 대기

장기 대기 임계치 초과는 `long_wait_count`, 자원 보유·대기 관계의 순환 검출은 `deadlock_cycle_count`로 분리한다. 진입 후에만 대기를 기록하면 영구 대기를 놓칠 수 있으므로 진행 중 대기 시간도 관측한다. 교착 회복은 안전 대기·우선권·허용된 후퇴 경로 등 명시적 정책으로 처리하며 점유 삭제나 순간이동으로 숨기지 않는다.

## 11. Rolling Horizon 실행 수명주기

### 11.1 기본 상태 전이

```text
READY → SNAPSHOT → QUEUED → SOLVING → RESULT_RECEIVED
                                      ├─ stale/invalid → REJECTED → FALLBACK/REPLAN
                                      └─ valid → RESERVED → EXECUTING_PREFIX → READY
reset/stop/close → CANCELLED (epoch 무효화, 실제 점유는 안전하게 정산)
```

요청 상태와 실제 로봇의 행동 상태를 한 필드로 합치지 않는다. 계산 중에도 다른 로봇과 GUI는 진행된다.

### 11.2 주기와 이벤트

- 기본 재계획: 5 sim-sec마다. 동일 event storm은 coalesce한다.
- 즉시 재계획: 확정 행동 완료, critical 도착, 자원 고장·폐쇄, 실제 처리시간 초과, 영향 있는 경로/설정 변경.
- 일반 작업 도착은 기존 계산을 무조건 연쇄 취소시키지 않는다. 영향 범위를 검사하고 최신 대기 요청에 반영한다.
- 진행 중 로봇의 불확실한 완료 시각 뒤에 후속 작업을 미리 확정하는 것은 초기 범위에서 제외한다. 실제 유휴 상태가 된 후 다음 계획에 포함한다.
- 바쁜 로봇을 계획 대상에서 제외해도 그 자원 점유·확정 예약은 포함한다.

### 11.3 짧은 실행 구간과 원자적 예약

- 다음 5초 안에 시작할 첫 유효 행동을 가진 로봇의 접두 구간을 검토한다.
- 접두 구간은 필요한 이동·대기를 포함해 첫 work 전체 또는 연속 charge 세션 전체까지다.
- “5초 실행 후 작업을 잘라 다시 배정”하는 뜻이 아니다.
- 후보 계획 전체를 장기간 확정하지 않는다. 실제 적용할 prefix만 예약한다.
- 적용 직전 로봇 가용성·작업 상태·예약·버전을 검증하고, 예약과 큐 제거·로봇 배정을 SimWorker에서 원자적으로 수행한다.
- 중간 실패 시 제거된 작업과 예약을 되돌리거나 명시적 부분 적용 결과를 남긴다. 한 작업에 두 활성 owner가 생기면 안 된다.
- 실제 SimPy Resource를 계속 사용한다. 예약만 믿고 실행 용량 검사를 우회하지 않는다.

### 11.4 오래된 결과

- request_id/engine_id/run_epoch가 맞지 않는 결과는 바로 폐기한다.
- 영향받는 로봇 위치·층·배터리, 작업 취소·허용 설비·전용 주문, 자원·경로·계수 변경을 검사한다.
- 전체 revision이 변했다는 이유만으로 무조건 폐기하지는 않는다. 영향 없는 신규 작업과 critical 변경을 구분한다.
- 초기 허용 지연 제안은 최대 5 sim-sec다. 이 값은 실제 검수로 조정한다.
- 시간 이동을 허용하면 절대 행동 시각·고정 점유·납기 비용·현재 배터리·전체 prefix를 다시 검증한다.
- 수락된 시간 이동 해는 `SHIFTED_FEASIBLE`로 표시한다. snapshot의 OPTIMAL을 현재 시각의 OPTIMAL로 복사하지 않는다.

### 11.5 지연·취소·복구

- 실제 작업이 길어지면 실제 점유를 연장하고 충돌하는 미시작 행동을 취소/재계획한다. 다른 로봇을 겹쳐 투입하지 않는다.
- 주문 취소는 미시작 작업을 제거하고, 진행 중 작업은 명시적 취소 프로토콜에 따라 정산한다. 취소 작업을 재등록하지 않는다.
- 작업 중단 시 이미 소비한 이동·작업 에너지를 한 번만 반영한다. 다시 시작한 시도와 이전 시도를 로그에서 구분한다.
- 정상 planning reserve 미만인 로봇은 새 일반 작업 대상에서 제외한다. 복구 모드는 남은 에너지로 도달 가능한 충전소와 안전한 자원 진입을 별도로 검증한다.
- 도달 불가이면 고장·구조 이벤트로 처리하고 시간·비용을 기록한다. 이를 정상 계획의 제약 만족으로 위장하지 않는다.
- 무해·시간 초과·계산 오류 시 공통 validator를 통과한 배터리/예약 인지 greedy prefix를 사용할 수 있다. 그것도 없으면 안전 대기다.
- fallback·복구·장기 작업 prefix는 원래 RH 해와 구분하고 횟수·시간·이유를 기록한다.

강제 충전·선충전·긴급 배정도 RH 모드에서는 공통 intent/검증/예약 경로를 거친다. `engine.assign()`이나 기존 `should_charge()/charge_target()` 규칙이 새 계획을 몰래 우회하지 않게 한다. 기존 배정 MILP가 기존 충전 규칙을 쓰는 것은 legacy 정책의 정의로 보존한다.

## 12. GUI·상태 설명·사용자 조작

### 12.1 화면에서 분리할 개념

| UI 항목 | 의미 |
|---|---|
| 실행 중 정책 | 실제 독립 엔진이 진행 중인 정책 목록 |
| 화면·개입 대상 | 좌측 로봇·KPI·수동 조치의 대상 엔진 |
| 비교할 정책 | 독립 실험에 포함할 정책 목록 |
| 계획 백엔드 | RH-MILP 또는 RH-CP-SAT, 모델/제약 범위 포함 |
| 비교 초기 상태 | 기본 배치·만충전 또는 별도로 구현한 상태 복제. 혼용 금지 |

- `최적화` 단독 라벨 대신 `가중치 휴리스틱`, `배정 MILP`, `RH-MILP`, `RH-CP-SAT`을 사용한다.
- 기본 실행에서도 로컬 최적화·비교 창을 사용할 수 있어야 한다. 문서 검색을 켜기 위해서만 RAG 설정이 필요하다.
- 솔버 패키지가 없으면 설치 방법과 비활성 이유를 보여주되 기존 시뮬레이터 전체가 import 단계에서 죽지 않게 한다.
- AI/RAG는 계산된 결과의 experiment_id·비용 가정·모델 범위·출처를 설명한다. 계산값을 문서 내용으로 덮어쓰거나 요청 없이 정책을 자동 적용하지 않는다.

### 12.2 실시간 실행 정책 관리

- 기본은 가벼운 기준 엔진들과 사용자가 선택한 RH 백엔드 1개를 실행하는 구성으로 시작한다. 정확한 기본 구성은 성능 검수 후 확정한다.
- MILP와 CP-SAT의 동시 실시간 실행은 고급 옵션이다. CPU 경쟁·메모리·예산을 표시하며, 이것을 단일 worker 독립 실험과 동일한 측정으로 취급하지 않는다.
- 이미 실행 중인 엔진 간 화면 전환은 시간·진행률을 초기화하지 않는다.
- 비실행 정책을 중간에 활성화할 때는 전체 비교를 동일 초기 상태에서 재시작하거나, 공통 현재 상태 복제가 구현된 경우 새로운 comparison_epoch를 만든다. 0초부터 새로 시작한 선을 기존 300초 선과 같은 실험처럼 겹치지 않는다.
- 중단된 정책의 그래프는 `중단/미실행`으로 표시한다. 0 처리량 선을 가짜로 이어 그리지 않는다.
- 이력은 engine_id·policy_id·run_epoch별로 보존한다. 화면을 전환했다고 하나의 배터리·대기열·타임라인에 서로 다른 엔진 표본을 섞지 않는다.
- 실시간 수동 개입은 선택 엔진에만 적용될 수 있으므로, 개입 이후 단순 그래프를 무개입 공정 비교라고 설명하지 않는다.

### 12.3 계획 상태·예약 표시

필수 표시:

- 현재 정책·백엔드·planner_scope·snapshot 시각·후보 수/전체 대기 수.
- 계산 중, 실행 가능, 해당 모델 최적, 대체 규칙, 무해, 오래된 결과 폐기, 설정 오류.
- solver 시간과 전체 적용 지연, 최근 단계별 목적값/경계.
- 선택 로봇의 다음 행동·작업·충전량·예약 시작/종료·예상 종료 잔량.
- 자원별 실제 점유와 확정 예약. 미확정 장기 계획은 다른 색/패턴으로 구분.
- fallback·overrun·stale·invalid 횟수와 원인.

`OPTIMAL` 툴팁은 “해당 snapshot·후보·계획 구간·제약·정수화 모델에서의 최적”이라고 설명한다. 전체 공장 미래나 실제 결과의 최적성으로 표시하지 않는다. 모형 밖 교통 자원이 있으면 해당 범위 경고를 항상 확인 가능하게 한다.

### 12.4 설정과 기본값 제안

| 설정 | 기본값 | 제안 범위·주의 |
|---|---:|---|
| horizon | 60 sim-sec | 최대 300, 실제 H_eff 표시 |
| step | 1 sim-sec | 검증된 0.5/1/2 프로필 |
| replan_interval | 5 sim-sec | 계획 구간 이하, 잦은 요청 coalesce |
| solve_soft_budget | 2 wall-sec | 모델 생성 포함 |
| solve_hard_budget | 3 wall-sec | 별도 프로세스 감시, 성능 프로필별 조정 |
| candidate_limit | 8 | 1~32, scope/규모 상한 검사 |
| processing_sigma | 1 | 0~3 초기 검증 범위, 확률 보장 아님 |
| energy_quantum | 0.001 배터리 단위 | 비교 모델에서 공통·실험 중 고정 |
| max_result_lag | 5 sim-sec | 수락 전 재검증 필수 |
| solver_threads | 1 | 공정한 기준 실험의 기본 |
| arc_limit | 60,000 | 초과 시 명시적 축소 안내/대체 처리 |

NaN·Infinity·음수·소수 후보 개수·해석 불가능한 단위는 거부한다. 설정 변경은 엔진의 공용 변경 API를 거치며 model_hash와 in-flight 결과의 유효성을 갱신한다.

**MVP의 실시간 지원 속도는 1x를 기준으로 검수한다.** 5x에서 solver가 2 wall-sec 걸리면 10 sim-sec가 지나므로 5초 지연 기준을 넘을 수 있다. 고배속은 결과 폐기·대체 규칙 비율을 보여주며, 자동 적응을 켜지 않은 상태에서 몰래 시간축을 멈추거나 예산을 늘리지 않는다.

## 13. 공정한 실험·재현성 요구

### 13.1 반드시 비교할 정책

독립 실험기는 `baseline_fifo`, `weighted_heuristic`, `assignment_milp_legacy`, `rh_milp`, `rh_cpsat`을 선택 실행할 수 있어야 한다. GUI 기본 선택은 Baseline·가중치 휴리스틱·선택 RH 정책처럼 제한할 수 있지만, 기존 휴리스틱을 대조군에서 빠뜨리지 않는다.

두 종류의 실험을 구분한다:

1. **알고리즘/솔버 품질 실험:** 고정 sim-time trace를 headless로 재생하고 계산 동안 sim-time은 진행하지 않는다. 제한된 wall 예산에서 계획 품질·처리 결과·실제 계산 비용을 각각 기록한다.
2. **운영 지연 실험:** GUI와 같은 비동기 실행으로 1x/2x/고배속에서 계산 지연·해 폐기·fallback·UI 응답성을 평가한다.

첫 실험의 결과를 실제 비동기 운영에서도 동일한 성능이라고 주장하지 않는다.

### 13.2 공통 입력

- 공장 구성·활성 자원·로봇 초기 위치/층/잔량·주문 초기 상태를 동일하게 한다.
- 외부 도착 trace를 정책과 무관하게 한 번 생성한다. 한 정책의 큐가 길다는 이유로 그 정책에만 도착 작업을 생략하지 않는다.
- 안정 task_uid·operation_uid·시도 ID를 사용한다. 선점·재등록을 새 외부 수요로 중복 계산하지 않는다.
- 작업별 공통 표준 난수와 설비별 처리 분포를 사용한다. 같은 작업·설비·시도에는 같은 표본이 재현되어야 한다. 미래 표본은 솔버에 노출하지 않는다.
- 고장·복구·용량 변경·수동 개입은 공통 외부 event trace로 제공한다. 상태에 반응하는 정책 고유 조치는 별도 treatment로 기록한다.
- 주문 기반의 WIP 릴리즈는 정책 결과에 따라 달라질 수 있다. 동일 외부 주문과 동일 릴리즈 규칙을 사용하고, 접수 주문량과 실제 릴리즈 작업량을 함께 보고한다.
- 선택 엔진의 DB 완료량이 다른 엔진의 실험 입력을 계속 바꾸지 않게 한다. 실험 입력은 동결된 사본이며 실험 진행률은 정책별로 독립 관리한다.

동일 seed라는 사실만으로 공정성을 인정하지 않는다. 입력 trace_hash, 공장/초기 상태 hash, 작업별 표본 계약을 확인해야 한다.

### 13.3 계산 조건

- RH-MILP와 RH-CP-SAT의 솔버 비교에서는 candidate 집합·모델 hash·단위·목적·예산·threads가 동일해야 한다.
- legacy/휴리스틱의 고유 후보 규칙 차이는 알고리즘 특성으로 기록한다. 필요하면 후보 수를 맞춘 ablation을 추가한다.
- 정책 비교에서는 각 최적화 정책에 같은 최대 가용 계산 예산을 주는 프로필을 기본으로 한다. 기존 배정 MILP의 0.25초 설정을 그대로 재현하는 프로필은 `legacy_exact_budget`으로 구분한다. 빠른 휴리스틱이 예산을 모두 소비하도록 인위적으로 기다리게 하지는 않는다.
- 실패한 정책·반복을 제거하고 성공한 결과만 평균 내지 않는다.
- 전체 실험 시간 제한으로 일부 정책이 끝나지 않으면 미완료 실험으로 표시한다. 끝난 반복만으로 공정한 추천을 만들지 않는다.
- 예산·후보·horizon 자동 축소는 기본 비교에서 비활성화한다. 사용하면 축소 이력과 별도 adaptive 프로필로 비교한다.
- seed는 외부 수요 seed와 solver 탐색 seed를 구분한다. 하드웨어·OS·라이브러리·worker 수를 기록한다.
- 입력 재현과 제한시간 솔버 해의 bitwise 재현을 구분한다. 다른 장비·버전·실행 부하에서 동일한 행동 순서를 보장한다고 쓰지 않는다.

### 13.4 실험 규모와 통계

| 목적 | 제안 프로토콜 | 해석 |
|---|---|---|
| GUI 시연 | 120초, 3개 시드, 명시적 가상 단가 | 동작 시연, 일반적 성능 우위 입증 아님 |
| 초기 스크리닝 | 대표 6개 시나리오, 5개 공통 시드, 300초 | 오류·병목·튜닝 방향 탐색 |
| 확인 실험 | 사전 선정한 대표 3개 시나리오, 최소 20개 공통 시드, 600초 이상 | 정책 차이의 불확실성 포함 보고 |
| 비동기 검수 | 기준 시나리오에서 1x/2x 및 실험적 5x/10x | 지연·fallback·응답성 검증 |

- 전체 조합을 무작정 곱하지 않고 대표 시나리오를 먼저 확정한다. 긴 실험은 CLI 배치를 사용한다.
- 워밍업·관측 구간·도착 중단 시점·drain 구간을 실험 파일에 명시한다. 지속 부하와 유한 작업 소진 실험을 섞지 않는다.
- 구간 시작 전 생성된 작업의 대기·완료를 어떻게 포함하는지 기록한다. 전체 완료량과 관측 구간 완료량을 분리한다.
- 정책 차이는 같은 seed의 쌍대 차이로 계산한다. 표본 수와 95% 구간을 보고하고, skew가 큰 지표는 paired bootstrap 등 보조 분석을 사용한다.
- 주요 비교 쌍과 주 지표를 튜닝 전에 정한다. 여러 정책·지표를 탐색한 결과는 탐색적 결과로 표시하고, 확증적 우위 주장에는 다중 비교 처리 방침을 명시한다.
- 솔버 목적값은 같은 Problem hash일 때만 직접 비교한다. 다른 시각·다른 후보의 목적값 평균을 정책 성능 순위로 사용하지 않는다.
- 평균 대기는 시작하지 못한 작업을 제외할 수 있다. 미완료 수·진행 중 대기·표본 수·P95를 반드시 함께 제시한다.

### 13.5 GUI와 CLI 작업 관리

- 비교는 UI 스레드 밖에서 수행하며 정책/seed 진행률·취소·실패 이유를 표시한다.
- 전체 작업의 예상 solve 횟수와 보수적 시간 상한을 보여준다. 기본 총 wall 상한은 300초 제안이며 큰 구성은 실행 전에 CLI 배치를 권장한다.
- GUI 상한을 넘는 정식 검증 실험은 CLI에서 시간·메모리·동시 실행 제한을 명시해 수행한다. 모든 실험을 기존 약 30초 제한 안에 끝내겠다고 약속하지 않는다.
- 사용자 취소나 총 예산 종료 시 자식 프로세스를 회수하고 이미 얻은 원시 결과를 `partial`로 저장할 수 있다. 이를 정상 완료 통계와 구분한다.

## 14. 지표·경제성·로그 계약

### 14.1 공통 운영 지표

| 구분 | 필수 지표 |
|---|---|
| 작업 보존 | 외부 접수 수, 릴리즈 수, 완료 수, 진행 중 수, 미배정 수, 취소 수, 중복 소유 위반 수 |
| 생산 성과 | 전체 완료·관측 구간 완료, 기존 슬라이딩 throughput, 전체 평균 처리율, 주문 납기 충족 |
| 대기 | 생성→배정, 배정→작업 시작, 순수 작업장 큐, 충전·통로·교차점·EV 대기 각각의 평균/P95/표본 수 |
| 미완료 작업 | 관측 종료 현재 대기, 가중 잔여 작업 비용, 후보 밖 작업 수, 최장 미서비스 시간 |
| 에너지 | 실제 이동거리, 이동·작업·대기·충전 증가 에너지, 외부 구조/설비 에너지의 포함 여부 |
| 계획 품질 | 단계별 incumbent/bound/status, 후보·arc·변수·제약 수, 모델/단위 버전 |
| 실행 품질 | accepted/stale/invalid/overrun/fallback/timeout/cancelled, 지연 분포, 예약 변경 수 |
| 안정성 | 자원 과점유·잘못된 층/경로·작업 중복·배터리 정산 오류, 장기 대기와 교착 구분 |

작업 수 보존식은 실행 시도와 외부 작업을 구분한 task_uid 기준으로 성립해야 한다. 재시도 횟수를 생산 완료 건수에 더하지 않는다. “공정 작업 1건”과 “완제품 1개”를 혼용하지 않는다.

로봇 가동률은 높을수록 무조건 좋은 목표가 아니다. 실제 이동/작업/충전/계획 대기/자원 대기/유휴를 분리해 비효율적인 이동 증가가 성능 개선처럼 보이지 않게 한다. `PLANNED_WAIT`를 생산적 작업으로 합산하지 않는다.

### 14.2 경제성 통일

공통 EconomicsModel은 다음 값을 명시적으로 받는다:

- 완료 단위와 건당 가치, 로봇별 에너지→Wh 환산값, 충전효율.
- 원/kWh 전력 단가, 전력을 제외한 이동 운영비, 평가 기간 고정비, 정책별 추가 비용.
- 실측/가상/추정 출처, 비용 적용 기간, 포함·제외 항목, model_version.

기본 계산 계약:

\[
E_{grid,Wh}=\sum_r \frac{E_{robot,r}\,k_r}{\eta_r},
\quad C_{power}=\frac{E_{grid,Wh}}{1000}p_{kWh}.
\]

\[
C_{total}=C_{power}+C_{move}+C_{fixed}+C_{policy},
\quad V=Qv,\quad P=V-C_{total}.
\]

\[
ROI_{op}=100\frac{P}{C_{total}}\quad(C_{total}>0).
\]

- 충전기·엘리베이터 설비 전력을 포함하지 않으면 추정 범위를 표시한다. 실제 콘센트 전력이라고 부르지 않는다.
- 이동거리×Wh/m 방식은 `legacy_distance_estimate`로 유지할 수 있지만 배터리 소모 기반 방식과 같은 수치 계약으로 섞지 않는다.
- 미설정은 null/N/A다. 알려진 매출 0원·무료 전력 0원과 미설정을 구분한다. 분모 0의 ROI를 0%로 조작하지 않는다.
- 반복별 ROI 평균과 전체 합산 순이익/비용의 pooled ROI는 다르다. 기본 요약은 pooled ROI로 명명하고 반복별 값도 저장한다.
- ROI 차이는 %p, 상대 변화는 %로 구분한다. 기준값 0이나 음수일 때 오해를 주는 상대 증가율 대신 절대 차이를 우선 표시한다.
- 새 모델을 도입해도 현 MILP 목적이 곧 ROI 직접 최적화라는 뜻은 아니다. 수익성은 운영 성과의 별도 평가다.
- 실제 투자비·감가상각·기간이 정의되지 않은 지표를 투자 ROI나 회수 기간이라고 부르지 않는다.
- 추천은 비교 조건·불확실성·미완료 작업·지원 범위를 함께 설명한다. 실측 없는 수익 보장은 금지한다.

### 14.3 내보내기와 추적성

실험 JSON/manifest와 선택적 CSV·JSONL에는 다음을 포함한다:

```text
schema_version / experiment_id / run_epoch / created_at / source_commit
policy_ids / backend_versions / model_version / objective_profile / planner_scope
units / rounding / model_hash / trace_hash / config_hash
factory_config / initial_state / external_orders / external_event_trace
seed_list / solver_seeds / worker_count / wall_budget / horizon / step / candidates
hardware / OS / Python / dependency_versions
per_seed_raw_metrics / aggregate_rules / paired_differences / uncertainty_intervals
solve_reports / acceptance_reports / fallback_and_failure_reasons
completed_and_unfinished_counts / energy_and_cost_assumptions / scope_warnings
run_status: complete | partial | cancelled | failed
```

- plan request→result→validation→reservation→action start/end→task state를 안정 ID로 연결한다.
- JSON에 API 키·인증정보·사용자 비공개 문서 본문을 넣지 않는다. 파일 경로와 사용자 이름 노출 정책도 정한다.
- 결과 파일의 임의 코드·pickle·문서 지시를 실행하지 않는다. 알 수 없는 schema/model_version은 조용히 현재 모델로 재생하지 않는다.
- 과도한 per-tick 로그는 샘플링/상한을 두되 위반·작업 생명주기·실패 원인은 보존한다. 샘플링 정책도 기록한다.

## 16. 비기능·성능·지원 조건

아래 숫자는 초기 제품 목표이며 아직 달성된 측정치가 아니다. 기준 하드웨어·OS·dependency lock을 확정한 뒤 계측한다.

| 항목 | 초기 검수 목표 |
|---|---|
| 기준 규모 | 로봇 5, 작업장 5, 충전소 3, 3층, 노드 500 이하, 후보 8, H=60, Δ=1 |
| 확장 실험 규모 | 로봇 10·후보 16·노드 1,000 수준부터 별도 성능 프로필로 검증 |
| 계획 계산 | soft 2 wall-sec, hard 감시 3 wall-sec. 모델 생성·solve와 전체 지연 각각 기록 |
| GUI 반응 | 기준 규모에서 입력 응답 P95 150ms 이하 제안, solver가 멈춰도 창 조작 가능 |
| 지원 1x 품질 | eligible 요청의 정상 해 수락률 90% 이상·fallback 5% 이하를 초기 목표로 제안 |
| 메모리 | 기본 planner 프로세스 1GiB 상한 제안, 초과 시 회수·명시적 실패 |
| 크기 제한 | arc 기본 60,000, 입력 단계에서 예상·실제 크기 확인 |
| 안정성 | 검수 trace에서 잘못 수락한 계획·작업 중복·미설명 자원 과점유 0건 |
| 플랫폼 | Python 3.11 이상. macOS/Windows/Linux별 승인 버전과 lock을 명시 |

- 요청이 불필요한 상태(작업 없음·유휴 로봇 없음)를 fallback으로 세어 비율을 왜곡하지 않는다.
- 정상 수락률의 분모는 완료된 eligible planning 요청이다. 전체 eligible prefix를 새 정상 계획으로 적용한 배치를 정상 수락으로 세고, 일부라도 대체 규칙을 사용한 배치는 mixed/fallback으로 따로 표시한다. fallback 비율은 같은 eligible 요청 중 해당 배치의 대체 규칙 사용 여부로 계산하며, 이벤트 횟수와 섞지 않는다.
- 0건 위반은 검수한 범위의 결과이며 실제 공장 전체에 대한 수학적 안전 인증을 뜻하지 않는다.
- 정상 모델의 예비 배터리 조건과 고장/구조 상태를 구분한다. baseline의 방전 이벤트를 자동으로 데이터 오류로 지우지 않는다.
- GUI thread는 파일 대량 저장·solver·긴 경로 전수 계산을 직접 수행하지 않는다.
- 패키지 버전은 공식 배포판으로 검증 후 고정한다. 기존 브랜치의 OR-Tools 검수 이력은 참고일 뿐 main의 전체 플랫폼 호환성 증거가 아니다.
- 최적화/RAG 의존성은 기능별 초기화·오류 안내를 분리한다. 네트워크나 외부 API를 자동 활성화하지 않는다.
- CI에는 정적 검사뿐 아니라 pytest와 headless/Qt offscreen 회귀를 포함한다. 실제 GUI 수동 검수 결과는 별도 기록한다.

### 16.1 성능 우위 및 기본 정책 전환 게이트

기능 통합만으로 기본 정책을 RH로 바꾸지 않는다. 다음은 승인 전 제안 목표다:

- 사전 선정한 병목 시나리오에서 강한 대조군인 가중치 휴리스틱 대비 완료량의 비열등성을 평가한다. 초기 허용 마진 제안은 5%다.
- 같은 평가에서 대기 P95 10% 감소를 개선 목표로 삼되, 미완료량 증가로 생긴 착시를 배제한다.
- 특정 시나리오에서만 개선되면 적용 조건과 실패 조건을 공개하고 opt-in으로 유지한다.
- CP-SAT이 MILP보다 빠르거나 좋은 결과를 내지 못해도 정확한 대체 백엔드 구현은 기능 완료로 인정한다. 기본 선택 변경은 별도 실험 결론이다.
- 성능 목표 미달을 숨기기 위해 난수·단가·후보·계획 구간을 유리하게 바꾼 결과만 제출하지 않는다.

M3는 단순한 capacity 제약 추가 작업이 아니다. 캐빈 상태와 실행 자원의 변경까지 포함하므로 별도 검토가 필요하다. 범위를 줄이면 출시 이름과 지원 범위도 줄여야 한다.

### 17.1 권장 변경 단위

각 단위는 독립 검수 가능한 변경 묶음으로 계획한다. 아래 목록은 실제 PR 생성 요청이나 승인으로 해석하지 않는다.

1. 물리 정확성 회귀·수정 및 단위 계약.
2. 정책 레지스트리·DTO·공통 builder·validator.
3. RH 컨트롤러·예약·prefix 실행·snapshot 무효화.
4. MILP 백엔드·두 단계·실패 처리.
5. CP-SAT 동등 모델·정수화·parity.
6. 다중 정책 실험·export/replay·공통 경제성.
7. GUI·RAG 분리·진단·예약 표시.
8. 교통 자원 및 캐빈 모델, 두 백엔드·실행 검수.
9. 확인 실험·플랫폼·문서·출시 체크리스트.

순서 6~7은 계약이 안정된 뒤 병행할 수 있다. 모든 변경 묶음은 main의 다층·RAG·ROI 기능을 보존하고, 기존 96개 테스트 및 관련 새 테스트를 통과해야 한다.

### 19.1 구현 전 승인할 ADR

| ADR | 권장안 | 미결 시 영향 |
|---|---|---|
| ADR-01 목적함수 | 가중 보류 우선 + 대기/지연/이동/충전, 초기 계수는 8장 | 결과 해석과 튜닝 목표 불명확 |
