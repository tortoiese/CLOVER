# 한국 사례 시나리오 실행 전 검수·보완 — 2026-11-17

판정: **수정된 개발 파일럿 입력을 실행할 수 있다.** 36입력/144정책의 전체 비교는 아직 실행하지 않았다. 개발 진단과 제한된 D1 canary를 통과했다는 뜻이며, 확인 실험 READY·모든 규모의 D1 지원·알고리즘 우세를 뜻하지 않는다. 실제 업체 제원/측정 trace가 아닌 합성 연구라는 범위도 유지한다.

최신 근거는 [검수 JSON](preflight_review_20261117.json)이다. 최초v1 `verification.json`과 이전 source의 결과는 과거 기록으로 보존한다.

위 변경은 개발 자료에서 병목 노출/정확성을 검수한 것이다. 서로 다른 초기/수정 입력의 납기율 차이를 알고리즘 개선율로 부르지 않는다. MILP나 CP-SAT의 우승을 기준으로 입력을 선택하지 않았고, 기본 optimized·가중치·수학 목적·2초 결정 예산을 바꾸지 않았다.

## 2. 참조 진단에서 확인한 기전

수정 source와 고정 `optimized`에서12조건×3seed의 원래2,100초 관측을 실행했다. 정책 순위를 정하는 비교가 아니라, 시나리오가 의도한 현상을 발생시키는지 확인한 개발 진단이다. 최초 실패 구성과 중간 개발 결과도 원래 파일에 보존한다.

- **통로 제한**: 같은 시각의 갱신 요청을 받은 clear와 restricted에서 실제 통로 대기 차이를 확인했다. 세 seed 모두 관측 종료의 물리 상태에서 원래2.2m로 복원됨을 확인했다. 시나리오당 처리량이 폭에 대해 반드시 단조로워야 한다는 가정은 하지 않는다.
- **갱신 시각/범위**:900/1200초는 변경/복원 요청 시각이다. 기존 점유가 있으면 안전한 drain 후 실제 geometry가 반영된다. 같은 폭의 sham은 geometry drain을 강제로 만들지 않으므로, 이 비교는 재구성을 포함한 운영 처치의 효과이며 정적 폭만의 인과효과를 분리한 실험이 아니다. 실제 용량 활성화 시각의 별도 분석 없이 정확히900~1200초 동안1차선이었다고 주장하지 않는다.
- **주문 급증**: KR03의 UID·목적지·우선순위·잡음·실제 총 작업 수를 유지한 burst에서 납기 압박이 나타났다. 조건 간 due 모집단은 경계 시각에 따라 달라질 수 있으므로 직접 조건 비교는 공통 UID 결과를 함께 확인해야 한다.
- **충전 경쟁**: 수정 후 모든 seed에서 충전이 발생했고, slot1에서 합산 충전 대기가 나타났다. 합산 대기 단위는 robot·s이며 개별 로봇의 경과시간과 다르다. 유한 창의 노출이며 정상상태나 충분한 충전 주기를 입증한 것은 아니다.
- **3층/캐빈**: 실제3층 목적지·연결 경로·충전 복귀 도달성을 확인했고, 두 캐빈을 켠 조건에서 두 캐빈의 실제 탑승 이동을 확인했다. 순환형 로보포트 재현으로 해석하지 않는다.

수정 참조36회는 모두 관측 종료·최종 물리 감사 통과, 고장/구조0이다. 이 결과만으로 baseline이나 RH도 모든 입력에서 안전하다고 추론하지 않는다. 후보/정책마다 실제 실행 상태를 별도 검수한다.

## 3. RH 반영 결과의 의미 변경

이전 source `fac6d32ab3cbc9168b6a945344b9d699da7012f8706432c3591abdd4bfa0c3ad`에서는 RH prefix가 commit된 뒤 보조 요청이 거절되면 최종 `accepted=false`로 바뀌었다. prefix 자체가 롤백된 것은 아니었다. 따라서 수락률과 fallback 횟수만으로 실제 RH 적용을 설명하기 어려웠다.

새 source `64b87519a8bb85517d432f24c376e018ede10933c92d40913f532747dc0bb295`의 `clover-rh-publication-receipt-v2`는 다음을 구분한다.

- `accepted=true`, `primary_accepted=true`: 실제 RH prefix 반영.
- `auxiliary_accepted=false`, `COMMITTED_AUXILIARY_DEFERRED`: 별도 보조 요청은 거절/보류. 해당 호출자에게 실패 통지.
- 이 경우 이미 반영한 prefix의 결정에 fallback을 추가 실행하지 않는다. 보조 거절은 receipt/사유에서 숨기지 않는다.

실제 작은 계획을 commit한 뒤 보조 요청을 거절시키는 회귀검사에서 작업 진행·물리 감사·fallback 부재·저장 결정 replay를 확인했다. 예전4,020회 결과나 `PARTIAL_AUXILIARY`의 의미를 새 해석으로 소급 수정하지 않는다. source가 다른 수락률/성능은 같은 비교로 합치지 않는다.

D1의 한 조건이 통과해도 이전 본 실험216건의 시간 실패가 해결됐다는 뜻이 아니다. 256노드나 더 큰 후보/대기열의 지원도 입증하지 않았다. 최종 운영 결론 전에 전체 대상 조건의 실패율·late primary·계산/검증/반영 비용과 fallback을 확인한다. 안전 검사에서 거부한 계획을 실행시키거나, 실패 seed를 성공할 때까지 반복해 빈도를 낮추지 않는다.

## 5. 실행 전 사용할 순서

1. 최신 recipe로 **새 디렉터리**에 생성하고 `audit_korean_case_pilot.py` 기본 validate로 검수한다. 예전 v1이나 source가 다른 묶음은 그대로 재사용하지 않는다.
2. `--stage d0-pilot --limit 1`로 기록 구조를 먼저 확인한다. 전체 개발 비교는 검수된 범위에서 `--limit 36`으로144정책 실행이다.
3. D1은 별도 출력과 `d1-diagnostic` stage로 진행하고, 다른 시뮬레이션과 동시에 돌리지 않는다. 성공·실패·미실행을 함께 남긴다.
4. 처리량/긴급 SLA뿐 아니라 후보 제외·보조 거부·실제 prefix 적용·고장/구조·진행 중 대기·에너지와 시간 예산을 함께 검토한다.
5. 실제 데이터/새 확인 표본이 준비되면 별도 등록으로 진행한다. 현재의 합성 개발 결과를 실제 한국 공장의 개선율로 발표하지 않는다.
