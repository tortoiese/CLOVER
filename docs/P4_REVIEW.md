## 이번에 바꾼 기능

집중 PRD의 M0~M6을 다음과 같이 구현했다. 자세한 계약은 [D1 사용 문서](../robot_factory_sim/D1_STARTUP.md)와 [집중 PRD](PRD_D1_STARTUP.md)에 있다.

| 단계 | 결과와 검증 방식 |
|---|---|
| M0 시간 장부 | 관측·계산·사전 검증·대체 비용을 구간별로 측정. 마지막 공개 비용은 여유를 먼저 지불하고 초과하면 실행 무효 표시 |
| M1 공통 입력 | 미래 noise 없는 불변 값 입력. baseline/optimized/legacy에 전체 보이는 작업을 주고 RH 후보 상한을 강요하지 않음 |
| M2 worker 수명 | 선택 정책 import/backend 구성 뒤 READY. session/generation/request 확인, timeout/RSS 감시·회수·bounded 재시작 |
| M3/M4 공통 실행 | 7개 정책의 배정·충전소·목표 갱신·선점을 같은 제안/최신 검사/적용 흐름에 연결. 최신 상태에서 안전하지 않으면 fallback/HOLD |
| M5 재현 | v5 결과, 결정·수명 기록/해시, 기록된 제안·지연 replay와 원시 로그 재분석, 종료 시 child/thread/연결/generator 회수 |
| M6 검수·문서 | 두 Python 전체 회귀, 물리 실행·재생·원시 지표, 강제 준비 실패·기간·예산·대조군, 실행 JSON과 동결 절차 |

RH 입력과 공통 관측을 같은 가상 시각에 캡처하도록 고쳤다.
다른 작업의 정상 도착은 실제 큐에 보존하고, 새 긴급 작업·참여 로봇/SOC/소유권 변화는 다시 검사한다.
worker READY에는 공장 문제의 사전 solve를 숨기지 않는다. 실패 계산·재준비·fallback 시간도 남긴다.
충전 목표를 판단하는 중에는 추가 충전을 보류하는 보수적 제어 의미를 사용한다.

`d1-staged-budget-v1`은 실제 측정 구간 + 선반영 공개 여유의 규약이다.
모든 비용이 실제 값과 정확히 같은 시간만큼 주입된다는 의미는 아니다.
내부 solver 시간과 외부 phase는 겹칠 수 있으므로 둘을 더해서 총 비용이라고 쓰지 않는다.

## 알고리즘별 관측한 차이

다음은 source A의 seed 1001, 단일 기계·worker 1개의 **개별 파일럿 관측값**이다.
신뢰구간, 산업 권장 제원, 보편적인 성능 순위가 아니다.
고정 trace·noise=0인 batch에서 seed 이름만 바꾼 결과는 독립 확률 반복으로 취급하지 않는다.

### 공동 배정: MILP가 좋아지는 실제 사례

| 정책 | D0 전체 2건 완료 시각 s | D1 전체 2건 완료 시각 s |
|---|---:|---:|
| baseline | 15.100 | 15.204 |
| optimized | 15.100 | 15.205 |
| assignment_milp_legacy | 15.800 | 11.725 |
| RH MILP grid | 12.500 | 12.688 |
| CP-SAT linear | 12.500 | 13.393 |
| CP-SAT 격자 interval | 12.500 | 13.778 |
| CP-SAT native 0.1s/4방문 | 11.300 | 12.319 |

가까운 작업을 하나씩 고르는 선택보다 여러 로봇·설비의 조합을 함께 고르는 것이 유리한 작은 예다.
MILP의 D0 배치 완료 시간은 휴리스틱보다 약 17.2% 짧다. 완료 수는 모두 2건이므로 이를 처리량 17.2% 증가라고 부르지 않는다.
D1에서는 시작 준비와 적용 시각도 결과에 들어간다. legacy가 D0와 다른 배정을 고른 결과까지 포함되므로 한 표를 solver 탐색 속도 순위로 읽지 않는다.

### 충전: 짧은 결과만으로 선택하면 안 됨

| 조건 | optimized 완료/도착 | MILP grid | native 0.1s/4방문 |
|---|---:|---:|---:|
| S04 한 슬롯, D0, 180s, seed 1001 | 13/14 | 13/14 | 14/14 |
| 같은 조건 D1, guard 0.1s | 14/14 | 14/14 | 10/14 |
| S04 한 슬롯, D1, 180s, seed 1002 | 16/17 | 15/17 | 16/17 |
| λ=0.08, D1, 1,800s, seed 1001 | 128/130 | 126/130 | 128/130 |

이 단순 배치에서는 긴 실행의 휴리스틱이 MILP보다 더 많이 완료했다.
MILP의 우세 사례를 만들려고 기본 가중치나 실패 결과를 바꾸지 않았다.
native의 D1 부진도 예산을 10초로 늘린다고 자동으로 해결되지 않았다.
재계획·충전 제어·동률 선택·stale/fallback·종료창이 모두 결과에 영향을 준다.

원인 분리를 위해 D0의 같은 180초 입력을 다시 비교했다.
native를 0.1s/4방문에서 2s/4방문으로 바꾸자 완료 수가 14→13이 되었고, 2s/전체 domain에서도 13이었다.
이 작은 사례에서는 세밀한 시간 단위의 영향이 확인됐고, 4방문 상한만으로 설명되지는 않았다.
이는 큰 문제의 전체 domain이 싸게 풀린다거나 두 formulation이 항상 같은 의미라는 주장이 아니다.

### 통로·교차로·캐빈: 환경을 바꾼 효과부터 확인

S02의 휴리스틱 D0 최종 완료 시각은 좁은 통로 168.8s, 넓은 통로 156.4s였다.
좁은 조건의 통로 대기는 60.2 robot·s, 넓은 조건의 설비 대기는 23.0 robot·s였다.
통로를 늘리면 다음 병목이 설비로 옮겨갈 수 있다. 처리량만 보면 모두 6/6이라 이 차이를 놓친다.

S03 초안은 교차로를 끄려고 `kind`를 바꾸었지만 모델의 실제 필드는 `node_type`이었다.
기존 A 파일럿의 S03 두 조건은 동일 자원 모델이므로 교차로 효과의 대조 증거에서 제외한다.
생성기를 `node_type`으로 수정하고 B에서 실제 traffic bundle의 교차로 자원 유무까지 확인했다.
`channel=intersection, resource=""`인 0초 통과 기록은 실제 교차로 점유 증거로 세지 않는다.
수정 결과는 별도 교차로 대조 receipt/CSV에 보존한다. 수정된 D0 seed 1001에서 교차로를 끄자 휴리스틱은 7/9→9/9 완료, 최종 완료 시각은 169.7→155.1s였다. MILP와 native도 7/9→9/9로 바뀌었다. 교차로가 켜진 조건에서 solver 교체만으로 자원 용량 한계를 제거하지 못했다.

S08은 두 조건 모두 두 샤프트의 좌표·링크를 유지하고 E1의 활성 여부만 바꾸었다.
치료 조건에서 실제 K=1 경로가 E와 E1 양쪽을 사용함을 확인했다.
휴리스틱 D0 완료 시각은 151.398→128.8s, 캐빈 대기는 10.902→0 robot·s였다.
완료 수는 둘 다 4건이다. 이 예에서는 알고리즘 교체보다 자원 구성을 개선하는 효과가 더 선명했다.

## 계산 비용과 실패를 해석하는 법

180초 S04 D1 seed 1001에서 optimized의 측정 phase 합은 약 0.63s였지만 공개 여유 합은 16.3s였다.
MILP는 각각 약 1.15s와 16.9s, native는 약 1.70s와 15.7s였다.
이 합은 여러 로봇의 일을 동시에 진행하는 벽시계 전체와 같지 않으며, 주입 시간 전체를 CPU 시간으로 해석해서도 안 된다.
반복 충전 목표 판단이 많은 정책은 고정 공개 여유의 영향을 더 크게 받는다.
따라서 D1 순위는 현재 구현한 정책·controller·규약의 순위이며, solver 자체 속도/수학적 품질의 순위가 아니다.

개발 중 0.05s 공개 여유를 0.1s로 늘린 뒤에도 긴 파일럿에서 0.136347s의 마지막 비용이 관측됐다.
해당 0.1s 실행은 `TIMING_COVERAGE_VIOLATION`으로 보존하고 유효 성공 표본에서 제외했다.
같은 입력의 모든 정책을 0.2s로 함께 재실행했고 7개 모두 통과했다.
새 실험용 JSON은 0.2s를 사용한다. 기존 기본 설정 0.1s와 이전 결과를 덮어쓰지 않는다.
다른 지도·컴퓨터에서도 0.2s가 반드시 충분하다고 보장하지 않는다. 초과 시 전체 정책의 같은 block을 새 규약으로 다시 비교한다.

1,800초 실험의 세 격자 formulation에서 한 번씩 최신 자원 용량 검사로 제안이 거부됐다.
원래 관측 시각의 계획은 독립 validator를 통과했지만 적용 시각의 잔여 용량과 충돌하여 적용되지 않았다.
이 세 건은 부적합 계획을 실행한 사건이 아니다. 최신 검사와 안전 대체가 작동한 기록이다.
legacy는 기존 이동+처리 60초 후보 제한과 soft 0.25초 native 제한을 유지하므로 RH와 지원 범위도 다르다.

## 다음 실험 환경의 권장 구성

1. **기전 확인**: 현재 10개 작은 JSON에서 하나의 자원·흐름만 바꾼 대조군을 사용한다. 배치의 makespan, burst의 미완료, stream의 rate를 구분한다.
2. **규모 확장**: 팀원이 준비한 4/8 로봇·64/256 node 배치를 각각 JSON으로 고정한다. 노드 수보다 실제 병목을 지나는 흐름, 길이, 방향, 설비·캐빈 이용률이 중요하다. 작은 지도를 최종 팀 지도라고 부르지 않는다.
3. **통로 단위**: 현재 로봇 폭 0.6m, side clearance 0.3m, 총 wall reserve 0.4m이면 demand=900mm다. 폭 1.3/2.2/3.1m는 용량 1/2/3대 조건이다. 폭 1.0m는 통과 불가 조건으로 별도 분리한다.
4. **병목 구성**: 같은 길이/수요/초기 상태에서 통로 폭, 교차로 유무, 충전 1/4슬롯, 캐빈 1/2기만 바꾼다. 실제 경로 선택·자원 요청을 먼저 감사하고, 추가 자원이 사용되지 않는 지도를 성능 대조로 쓰지 않는다.
5. **모델 비교**: grid/linear/격자 interval은 같은 문제로 비교한다. native 2s/전체 domain은 의미 대조, 0.1s/4·8방문은 다른 운영 설정으로 별도 표기한다. 품질과 timeout/build/RSS를 함께 기록한다.
6. **시간 비교**: D0는 계획 선택의 효과, D1은 준비/판단 지연을 포함한 효과로 각각 제시한다. 예산 0.5/2/10초, cold on_demand/eager를 training에서 비교한다. 0.5초 cold 성공은 가정하지 않는다.
7. **부하 선정**: λ=0.04/0.08부터 시작해 실제 병목 포화 전후를 찾는다. λ=0.08을 모든 정책에서 과부하라고 미리 이름 붙이지 않는다. 유한 구간 backlog 기울기와 완료율로 구분한다.
8. **한도**: solver 한 개씩, native thread=1, 동일 timeout/watchdog/RSS 한도, 동일 trace/초기 상태. 다른 CPU 부하를 피하고 CPU·RAM·OS·Python·backend 버전을 기록한다. 이 파일럿은 macOS arm64이며 다른 OS를 검증한 것은 아니다.

### 기간과 충전 순환

600/1,800초 probe의 300초 구간별 도착·완료·미완료를 [duration_bins.csv](P4_EVIDENCE/duration_bins.csv)에 보존했다.
λ=0.08의 baseline 미완료는 7→15→33→43→56→70으로 늘었지만 optimized는 2→1→0→1→0→2였다.
이는 해당 입력의 정책별 운용 차이다. 도착률만으로 공장 전체의 물리 용량 한계를 계산한 결과가 아니다.

1,800초의 총 충전량/전체 배터리 용량 비는 λ=0.04에서 대부분 약 0.84~1.13회, λ=0.08의 주요 정책은 약 2.02~2.89회였다.
이 비는 에너지 환산 지표이며 로봇 한 대 한 대가 여러 충·방전 주기를 완료했다는 증거가 아니다.
따라서 최종 충전 효과 판단에 180초나 600초만 쓰지 않는다.
다음 training의 시작안은 **warm-up 600초 + 측정 7,200초**다. 이를 정상상태로 검증했다고 주장하지 않는다.
E1에서 정책별 로봇 에너지 순환·구간별 WIP/rate·긴급 응답을 확인한 뒤 환경별 공통 W/T를 E2 전에 고정한다.
불안정/과부하 조건에는 정상상태 평균 대신 고정 기간의 backlog 성장·납기 실패를 사용한다.

### 튜닝과 최종 검증의 분리

[P4_TRAINING_PROTOCOL.json](P4_TRAINING_PROTOCOL.json)은 이번 코드·10개 진단 입력·생성기와 다음 training 후보를 고정한다.
탐색 seed는 1000대, tuning은 10001~10005, validation은 11001~11010, held-out 예약은 20001~20030이다.
숫자만 분리해서 같은 지도를 최종 검증했다고 하지 않는다. held-out 지도·거리·방향도 새로 확보한다.
후보 설정을 전수 곱하지 않고 같은 기준에서 한 요소씩 바꾸어 품질/계산량을 확인한다.

E2는 `enabled=false`, 최종 입력 목록은 아직 비어 있다.
실제 팀 지도, E1의 최종 선택 설정, 측정창·drain, 주 지표·규칙을 확정한 별도 protocol 없이는 본 실험을 시작하지 않는다.
현재 학습 결과, 신뢰구간, 자동 선택기, 일반화 추천은 없다.

## 실행과 재현

저장소 루트에서 의존성을 설치한 후 다음을 실행한다.

```bash
python -m pip install -r robot_factory_sim/requirements-headless.txt
python -m pip install -r robot_factory_sim/requirements-planning.txt
python -m pip install -r robot_factory_sim/requirements-legacy.txt

# 새 출력 경로를 사용한다. prepare는 입력과 코드/생성기 해시를 동결한다.
CLOVER_P4_OUTPUT=/tmp/clover-new-pilot python tools/p4_pilot.py prepare
CLOVER_P4_OUTPUT=/tmp/clover-new-pilot python tools/p4_pilot.py d0
CLOVER_P4_OUTPUT=/tmp/clover-new-pilot python tools/p4_pilot.py d1
```

같은 해시의 저장 결과를 재생·원시 분석하는 명령은 `python -m simulation.evaluation --help` 및 D1 문서에 있다.
A의 과거 결과는 A 코드/보존 소스에서 재생해야 한다. B로 바꿔서 source 검사를 끄지 않는다.
생성기 수정 전 A의 S03 대조 오류·0.1s 실패를 삭제하거나 새 입력/설정의 결과로 바꾸지 않는다.
새 생성기는 수정된 S03·guard 0.2s·현재 source hash로 새 protocol을 만들므로 과거 A 결과와 byte 동일한 성과를 보장하는 명령이 아니다.
