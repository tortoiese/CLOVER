# 통행 자원 계약 및 GUI 적용 명세

최신 실패 계측·동일 문제 구성 개선·profile CLI는 `NATIVE_PROFILE_AND_BUDGETS.md`를 참고한다.

최신 자유 시작시각 CP-SAT의 해상도·전체/제한 domain은 `NATIVE_SCHEDULING.md`를 참고한다.

계약 버전: **`traffic-mm-bundle-v1`**. 경로 탐색, 실제 SimPy 진입,
관측 스냅샷 및 후속 계획기의 예약 변환은 아래 단위와 수명 규칙을 공유한다.
기본 스케줄러는 기존 **가중치 휴리스틱(`optimized`)**을 유지한다.

## 실행과 시연

프로젝트 Python 3.11+ 환경에서 `python -m pip install -r requirements.txt` 후 실행한다.

```bash
cd robot_factory_sim
python main.py
```

설정 없이 병목을 시연하려면:

```bash
python traffic_demo.py --width 1.3 --robots 6
```

시연은 임시 DB에서 중앙복도형 공장을 만들고 실행한다. 기존 공장 DB를 변경하지 않는다.
창을 닫으면 임시 DB를 정리한다. 중앙 통로는 좁은 양방향 통로이고 좌측 조립 진입로는 일방통행이다.
시뮬레이션을 진행하면 자원 확보 경쟁에 따른 대기가 표시된다. 필요하면 GUI 배속을 높인다.

## 편집 방법

- **공장 설정 → 로봇 관리:** 로봇 폭·길이를 m 단위로 입력한다. 음수·0·NaN·무한대는 거부한다.
- **공장 설정 → 선택/이동:** 통로 선을 선택하면 폭과 양방향 여부를 편집한다.
- **시작·끝 방향 뒤집기:** 일방통행 방향을 바꾼다. 양방향 체크를 끄면 시작→끝만 허용한다.
- **일반 경로 노드 선택:** 노드 유형을 `intersection`으로 바꾸면 교차로 자원이 된다.
  설비·충전소·엘리베이터에 연결된 노드는 유형 변경을 막아 연결을 보존한다.
- **저장:** 기존 DB 컬럼과 변경 이력으로 저장하고 핫리로드한다. 별도 스키마 변경은 없다.
- **층 도면 → 통행·병목:** 방향·통행 불가·점유 예약·대기 오버레이를 켜고 끈다.

## 통행 규칙

| 항목 | 적용 기준 |
|---|---|
| 최소 통행 폭 | `demand_mm(robot_width) <= capacity_mm(edge_width)` |
| 입력 단위 | 통로·로봇 폭과 길이: m, 도면 좌표: px, 시간: sim-sec |
| 확보 단위 | 통로: 정수 mm, 교차로: slot(1대), 캐빈: 기존 설정 대수(slot) |
| 기본 여유 | 벽 여유 0.4m + 측면 여유 0.3m. 실제 기준은 공장 프로필 값 |
| 폭별 경로 | 로봇 폭별로 통과 불가 엣지를 제외하고 경로·거리를 계산 |
| 일방통행 | `is_bidirectional=False`인 엣지는 시작→끝 방향만 허용 |
| 경로망 진입 | 최근접 가시 노드로만 진입. 먼 노드로 바로 붙어 폭·방향 제한을 우회하지 않음 |
| 좁은 통로 | 통과 가능한 활성 로봇 중 가장 넓은 로봇 2대가 나란히 들어가지 못하는 연속 구간을 묶음 |
| 연속 구간 경계 | 분기 없는 일반 노드만 연결. 교차로는 별도 자원으로 연결하고 설비·충전소는 경계 |
| 확보 방식 | 묶인 구간의 모든 통로 폭과 교차로 슬롯을 단일 arbiter에서 한꺼번에 승인. 부분 확보 없음 |
| 교차로 | 중심으로 진입하기 전에 교차로와 경로상 출구 구간을 확보 |
| 자원 순서 | 단일 승인 연산으로 전체 묶음을 확보하므로 자원 ID나 요청 순서에 의존하지 않음 |
| 대기 순서 | 겹치는 자원을 요청한 묶음 사이 FIFO. 무관한 자원 요청은 계속 진행 |
| 대기 위치 | 제어 구간 진입 직전의 경로 노드. 확보 전에는 로봇 위치를 진행시키지 않음 |
| 크기 변경 | 이미 확보한 구간에서는 기존 크기를 유지하고, 해제 후 새 크기를 적용 |
| 진입 전 취소 | 대기 묶음 전체를 제거하고 계측·대기 원인을 정리 |
| 진입 후 취소 | 취소·재경로·퇴역 명령을 보류하고 출구 도착 + 후미 여유 후 처리. 퇴역 명령 우선 보존 |
| 해제 | 정상 종료·예외 정리 모두 동일 묶음의 소유권을 한 번만 해제. 중복 해제는 무해 |
| 방전 | 멈춘 로봇의 점유 유지 → 구조 대기 → 복구 후 출구로 이동 → 후미 여유 후 해제 |
| 핫리로드 | 구조 변경은 신규 진입을 닫고 기존 통로·캐빈 소유자가 비워진 뒤 적용. 마지막 저장 설정 사용 |

예: 폭 0.6m 로봇과 기본 여유 설정은 1.3m 통로를 통과할 수 있고, 1.29m 통로는 통과할 수 없다.
로봇이 물리적으로 들어갈 수 있는지 먼저 검사하고, 기준 로봇 차선 수로 환산하지 않는다.
현재 브랜치의 실행 정책은 베이스라인·가중치 휴리스틱 두 가지이며, 둘 다 같은 주행 가능 후보 제약을 적용한다.
배정·충전 목적함수의 새 알고리즘을 구현한 것은 아니다.

### 폭 용량과 점유량

입력 통로 폭을 `W`, 벽 전체 여유를 `E`, 로봇 폭을 `w`, 로봇별 측면 여유를 `S`라 하면:

```text
C = max(0, floor(1000 × (W - E)))  # 사용 가능한 정수 mm
q = ceil(1000 × (w + S))           # 로봇 1대가 확보하는 정수 mm
진입 조건: q <= C, 그리고 기존 확보량 합계 + q <= C
```

벽 여유는 통로에서 한 번 빼고 측면 여유는 로봇마다 부과한다. 소수 계산은 Decimal을 사용한다.
용량은 내림, 수요는 올림하므로 1mm 미만 차이로 큰 로봇을 통과시키지 않는다.
통로보다 큰 수요를 용량에 맞춰 줄이는 clamp는 금지한다.
예를 들어 2.7m 통로의 용량은 2300mm이며, 0.6m·1.1m 로봇은 각각 900·1400mm를 확보해 함께 들어갈 수 있다.
교차로는 폭 합계와 별개인 1 slot이며 묶음 승인 시 함께 확보한다.

자원 ID는 DB 번호 대신 층·양 끝점 좌표를 사용한다. 역방향·중복 엣지는 같은 자원을 참조하고
서로 다른 폭이 입력되면 최솟값을 사용한다. 경로 탐색도 같은 최솟값을 적용한다.
번호 변경은 점유를 초기화하지 않는다. 제거되거나 축소된 자원의 기존 소유자는 보존하고 신규 승인은 막는다.

### 확보 구간과 해제 시점

로봇 중심이 출구에 도착해도 바로 해제하지 않는다. 기존 교차로 통과 시간에 더해
`robot_length / (2 × max(0.05, speed))`초의 후미 여유를 둔다.
묶음의 모든 자원은 첫 구간 진입 승인부터 이 시점까지 함께 보유한다.
구간 안에서 예정 시각을 기다리는 시간이나 구조 시간도 보유 시간에 포함한다.

구조 변경이 요청되면 엔진은 기존 레이아웃을 유지하고 모든 신규 통로 진입 및 신규 작업 배정을 닫는다.
대기 로봇의 미승인 요청은 취소하고, 승인된 로봇과 캐빈이 비워진 다음 디스패치 틱에서 새 구성을 적용한다.
그동안 추가 저장하면 마지막 구성을 적용하며, 원래 구성을 저장하면 변경 대기를 취소한다.
이는 이동 중인 자원을 새 객체로 바꿔 이중 승인을 만드는 것을 방지한다.
리셋은 기존 시뮬레이션 전체를 버리고 새 환경과 자원을 생성하는 별도 경계이다.

### RH MILP / CP-SAT 연결 계약

`TrafficDemand`와 `TrafficReservation`은 SimPy/Qt 참조가 없는 불변 데이터이다.
각 행은 `resource`, `amount`, `unit`, `contract`를 가진다. 예약 시간은 절대 sim-sec의 반개구간 `[start, end)`이다.
`section_end`와 `section_demands`는 실행·계획이 같은 통제 구간을 만들도록 한다.
`planned_reservations`는 구간 내 모든 자원에 **같은 전체 점유 시간**을 부여하고,
구간 간 후미 여유가 없는 일정은 거부한다. 현재 확보량·대기열은 같은 자원의 관측값으로 읽어야 한다.
예약 데이터 생성은 자원을 실제로 확보하거나 미래 진입을 보장하지 않는다. 실제 진입은 arbiter가 다시 검사한다.

후속 PR #10의 계획기는 이 계약에 맞춘 재기반·어댑터 수정이 필요하다.
MILP 용량 제약과 CP-SAT cumulative에는 통로 mm를, 교차로와 캐빈에는 slot을 사용해야 하며,
독립 엣지별 이동 시간만 예약하지 말고 위 묶음 전체 시간과 후미 여유를 포함해야 한다.
캐빈은 `bind_elevators`가 참조하는 엔진의 실제 자원을 사용한다.
본 PR은 RH 계획기와 캐빈·출입구 통합 예약을 추가하지 않는다.

## 화면 표시와 지표

- 회색: 미사용 통로, 초록: 자원 확보(진입 예약 포함), 노랑: 요청 대기, 빨강: 통행 불가.
- 화살표: 일방통행 방향. 원형 표시: 명시적으로 지정한 교차로.
- 노란 점선 로봇: 실제 통행 자원을 기다리는 상태.
- 통로/로봇에 마우스를 올리면 폭·점유 예약·요청 순서·대기 원인·시간을 확인한다.
- 공장 요약: 통행 대기 로봇 수, 대기열이 있는 자원 수, 현재 최장 대기시간.
- `intersection_wait`: 교차로 자원 확보 대기시간. 통로 대기와 별도로 계측한다.
- 기존 `deadlock_count` 키는 호환성을 유지하되 **장기 통행 대기**로 표시한다.
  120초를 넘겨 해소/취소된 대기의 횟수이며 수학적으로 증명된 교착 건수가 아니다.
- 확보량은 실제 위치 점유만이 아니라 진입 전 예약도 포함한다. 위치는 로봇 아이콘으로 확인한다.
- 통로 도움말의 확보량은 mm를 m로 바꿔 표시하고, 교차로는 대수로 표시한다.
- `변경 적용 대기`는 기존 점유를 보호하며 신규 진입을 막는 상태이다. 용량이 0이어도 기존 확보량이 남을 수 있다.
- 병목 표시의 적색 여부는 현재 활성 로봇 중 통과 가능한 크기가 있는지와 장애물 여부 기준이다.
  일부 작은 로봇만 통과할 수 있는 길은 개별 로봇의 경로 탐색에서 다시 검사한다.

## 갱신 부하 개선

- 고정 통로 도형·화살표는 레이아웃 변경 때만 재생성한다.
- 통행 오버레이는 최대 5Hz로 반영하고, 변화가 있는 아이템의 펜·라벨·도움말만 수정한다.
- 같은 로봇 경로·층·긴급 상태는 경로 도형을 재생성하지 않는다.
- 현재 층 밖의 로봇 경로와 숨겨진 도면의 애니메이션 갱신을 줄인다.
- 일반 로봇은 긴급 로봇의 깜빡임 위상만 바뀌었을 때 다시 그리지 않는다.
- 동일 상태를 100회 반영하는 테스트에서 초기 생성 이후 추가 경로 재생성 0회를 확인한다.
  이 검증은 렌더링 작업 감소 검증이며 FPS나 전체 GUI 성능의 배수 향상을 의미하지 않는다.

## 검증 방법

```bash
QT_QPA_PLATFORM=offscreen MPLCONFIGDIR=/tmp/factory-mpl PYTHONDONTWRITEBYTECODE=1 \
  python -m pytest -q -p no:cacheprovider
```

폭 경계값·보수적 반올림·이종 로봇 합산, 우회 경로, 역주행 차단, 복수 자원 일괄 확보,
FIFO·대기 취소·무관한 요청 진행, 중복 엣지·안정적 식별자, 축소·삭제·핫리로드 장벽,
후미 여유·직접 인터럽트·방전 구조·캐빈 실제 도착, 계획 예약과 실행 시간 일치,
DB 저장, GUI 단위·대기 원인·층 전환·갱신 제한 및 종료를 검증한다.
렌더링을 통해 통행·병목 화면과 편집 창의 배치도 확인한다.
GitHub Actions는 Linux/macOS/Windows × Python 3.11/3.14에서 pytest·의존성 호환성·계약 코드 Ruff를 실행한다.

## 적용 한계와 후속 합의

- 공유자원 기반 통행 근사 모델이다. 로봇 외형의 연속 충돌 판정·회전 궤적·차선별 실제 좌표는 모델링하지 않는다.
- 분기점은 교차로로 지정해야 상호배제가 적용된다. 그림의 선이 교차하기만 해서는 교차로가 생성되지 않는다.
- 별도의 주차 면적·대기 위치 용량을 모델링하지 않는다. 같은 진입점의 로봇 아이콘이 겹칠 수 있다.
- 자원 확보·요청 순서의 교착을 줄이는 규칙이며 모든 환경의 공간적 교착 부재를 증명하지 않는다.
- 긴 연속 구간의 사전 확보는 안전 쪽으로 보수적이어서 처리량을 줄일 수 있다.
- 엘리베이터 탑승 후 취소는 실제 도착까지 보류하고, 자원 조회는 실제 캐빈과 공유한다.
  출입구 교통과 캐빈의 통합 최적화, 여러 로봇의 동일 캐빈 동승 운행 제어는 후속 범위다.
- 실제 로봇 제원·통로 안전 여유, 작업 우선순위에 따른 통행 규칙, 다층 발표 범위는 팀 합의가 필요하다.
- Windows/Linux의 눈으로 보는 데스크톱 GUI 및 다양한 로봇 수의 FPS 측정은 별도 검증 대상이다.
